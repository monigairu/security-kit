## 1. この文書について

### 1.1 目的

要件定義書 v0.5 の要件を、どの部品で、どのような流れで実現するかを決める。

### 1.2 今回詳しく書く範囲

キットの中心は「先輩役」と「コードのレビュー」なので、今回はこの2つを詳しく書く。

| 範囲 | 書き方 | 該当要件 |
|---|---|---|
| 先輩役（声かけ・説明・相談） | 詳しく | FR-10〜19 |
| 例外と誤検知の扱い | 詳しく | FR-41、FR-46 |
| ルールと検査ツールの対応付け | 詳しく | FR-01〜08 |
| コミット前チェック | 詳しく | FR-28 |
| PR 時の最終チェック | 詳しく | FR-30〜39 |
| 記録 | 詳しく | FR-40〜45 |
| テスト | 詳しく | NFR-06、NFR-07 |
| 安全装置 | 概要のみ（次版で詳しく） | FR-20〜27、FR-29、FR-76 |
| 配布とセットアップ | 概要のみ（次版で詳しく） | FR-70〜75 |
| ルールの保守 | 概要のみ（次版で詳しく） | FR-50〜56 |
| 監査役、強化版（Lv2） | 対象外（第二弾で設計） | FR-60〜64、FR-80〜84 |

### 1.3 設計の基本的な考え方

| 考え方 | 内容 |
|---|---|
| 止めるのは書く前、注意は書いた後 | 「止める」は書き込む前に判定して書かせない。「警告」「助言」は書いた後に伝える |
| 指摘は今回変えた部分だけ | 以前からある問題は伝えず、判定にも使わない。指摘があふれて無視されるのを防ぐ |
| 助言では作業を止めない | 作業を続けさせて修正を求めるのは「警告」以上だけ。「助言」は最後のまとめに載せる |
| 重い検査は後ろに回す | 書いた直後は速い検査だけ。時間のかかる検査は作業の区切りと PR 時に回す |
| AI への通知文は決まった型で | 指摘は毎回同じ型で Claude に伝える。通知文にコードの中身は入れない（NFR-13） |
| フックは追加インストールなしで動く | フックのスクリプトは Python の標準ライブラリだけで書く。依存ライブラリの乗っ取りの影響を受けず、起動も速い |
| 先輩役は止まっても開発は止めない | 検査ツールが無い・失敗したときは、先輩役は黙って飛ばし（1回だけ知らせる）、最後の砦は PR 時の検査とする |
| 止めたら逃げ道も示す | 誤って止めたときに開発が止まらないよう、除外と例外の方法を必ず用意する |

### 1.4 部品の書き方の使い分け

キットは3種類の書き方を組み合わせて作る。

| 種類 | 何で書くか | キットの部品 | 性質 |
|---|---|---|---|
| 自然言語 | Markdown | Skill、CLAUDE.md、AGENTS.md | AI が読んで従う。従わないこともある |
| 設定 | JSON、YAML | 強制設定、フックの登録、ルール、GitHub Actions | Claude Code や GitHub が必ず守る |
| プログラム | Python | フックのスクリプト、build.py、PR の判定 | 毎回同じ結果になる |

「止める」は設定とプログラムだけで行い、自然言語は「教える・説明する」に使う（NFR-03）。

## 2. 全体構成

### 2.1 部品のつながり

```
【開発者の PC】
  Claude Code
   ├─ 強制設定ファイル …… 止めるルールの土台（本人の設定より優先）
   ├─ リポジトリの設定 …… .claude/settings.json
   └─ security-kit プラグイン
        ├─ 声かけフック（書く前・書いた直後・作業の区切り）
        ├─ Skill（伝え方・ルールの説明・認可の確かめ方）
        ├─ 相談コマンド・報告コマンド・初期化コマンド
        └─ 検査スクリプト → 検査ツール（Ruff、gitleaks、Semgrep 等）
  コミット前チェック …… gitleaks（AI を通らない変更も対象）
  記録（補助）
        │
        │ push・PR
        ▼
【GitHub】
  PR 時の最終チェック
   ├─ 層1 検査ツール（GitHub Actions）
   ├─ 層2 別ベンダー AI（Codex）
   └─ 判定・PR へのコメント・記録（正とする記録）
```

## 3. 先輩役の設計

### 3.1 検査の3つのタイミングと重大度

検査は3つのタイミングで行い、重大度ごとに伝えるタイミングを分ける（FR-14）。

| タイミング | Claude Code の仕組み | 検査の中身 | 目標時間 | 見つけたときの動き |
|---|---|---|---|---|
| ① 書く前 | PreToolUse フック（ファイル書き込みの直前） | 書こうとしている内容の秘密情報（キット内蔵の判定） | 1 秒以内 | **止める**：書き込ませない |
| ② 書いた直後 | PostToolUse フック（ファイル書き込みの直後） | 書いたファイル1つだけ。Ruff のセキュリティルール（S）、キット独自の簡易チェック | 2 秒以内 | **警告**：すぐ Claude に伝える。**助言**：記録だけする |
| ③ 作業の区切り | Stop フック（Claude の応答が終わる時点） | このターンで変更したファイル。gitleaks、Semgrep、Trivy（構成ファイルがある場合） | 30 秒以内 | **警告**が残っていれば修正を求める（1回だけ）。**助言**はまとめに載せるだけ |
| ④ 作業の区切り（背景） | Stop フック（背景で動く） | このターンの差分の AI レビュー（3.14） | 待たせない（5〜30 秒） | 重大な指摘があれば Claude を呼び戻す |
| ⑤ コミットの直後（背景） | PostToolUse フック（git commit のとき。背景で動く） | コミットされた変更の AI レビュー。関係するファイルもたどる（3.14） | 待たせない（10〜60 秒） | 重大な指摘があれば Claude を呼び戻す |

```
 Claude がファイルを書こうとする
        │
        ▼
 ① 書く前の検査 ── 秘密情報あり ──▶ 書き込みを止める
        │ なし                        （理由・代わりの方法・除外や例外の方法を表示）
        ▼
 ファイルに書き込まれる
        │
        ▼
 ② 書いた直後の検査 ── 警告あり ──▶ Claude に通知 → 利用者に説明してから直す
        │                └ 助言あり ──▶ 記録だけして、③のまとめに載せる
        ▼
 （作業を続ける。①②を繰り返す）
        │
        ▼
 Claude が応答を終えようとする
        │
        ▼
 ③ 作業の区切りの検査 ── 警告が残っている ──▶ 応答を続けさせ、説明と修正を求める（1回だけ）
        │
        ▼
 作業のまとめを利用者に表示（出た指摘と対応状況。助言はここで伝える）
```

### 3.2 指摘を今回変えた部分に絞る方法

②と③では、ファイル全体を検査したうえで、今回変えた行に重なる指摘だけを伝える（FR-10、FR-18）。

| 対象 | 変えた行の求め方 |
|---|---|
| git で管理しているファイル | ターンの始め（利用者が指示を送った時点）に作業フォルダの状態を記録しておき、その時点との差から、変えた行の範囲を求める |
| 新しく作ったファイル | ファイル全体を対象にする |
| git で管理していないフォルダ | ファイル全体を対象にする |

- 変えていない行にある以前からの問題は、伝えず、記録もしない。
- 既存のプロジェクトへ入れるときは、初期化コマンドで一度だけ全体を検査し、既存の指摘の一覧を作る（FR-39）。直すかどうかは利用者が決める。
- ターンの始めの記録は、リポジトリの中身（作業フォルダ、ステージ、ブランチ）に手を加えない方法で行う。利用者がコミットせずに書いていた変更も「以前からあるもの」として扱える。
- 記録が無いとき（フックが動かなかった場合など）は、まだコミットしていない変更を対象にする。

### 3.3 ① 書く前の検査（止める）

| 項目 | 内容 |
|---|---|
| 対象 | Claude のファイル書き込み（Write、Edit） |
| 検査 | 書こうとしている内容（新しいファイルの中身、または書き換え後の部分）を、キット内蔵の判定にかける。見るのは、決まった書き出しを持つ鍵や秘密鍵のブロックなど、形だけで秘密情報とわかるものに限る（誤って止めることがほぼ無いものだけを止めるため） |
| gitleaks を使わない理由 | gitleaks は起動だけで約1秒かかり、書き込みのたびに待たせることになる（試作で実測）。gitleaks の全ルールによる検査は、作業の区切り（3.5）・コミット前（5章）・PR 時（6章）で行う |
| 止めたとき | 書き込みを拒否し、Claude に理由を返す。理由には、ルール ID、何が危ないか、安全な代わりの方法（例：環境変数から読む）、除外や例外の方法（3.11）を必ず入れる（FR-24） |
| 該当ルール | R-001（秘密情報をコードに直接書かない） |
| 除外 | 行に付けた印（3.11）と、プロジェクトの設定ファイルの「検査から外すフォルダ」に従う。印は gitleaks と同じもの（`gitleaks:allow`）を使い、書く前・コミット前・PR 時で判定を揃える。広く使われている見本の値（末尾が EXAMPLE のもの）は対象にしない |
| 警告モード | 止めずに②と同じ「警告」として伝える（FR-25） |

> Claude が Bash（コマンド）でファイルを書いた場合は、①の検査を通らない。これはコミット前チェック（5章）と PR 時の検査で止める。

### 3.4 ② 書いた直後の検査（警告）

| 項目 | 内容 |
|---|---|
| 対象 | Claude が書いたファイル1つ |
| 検査（Python ファイル） | Ruff のセキュリティルール（S。Bandit のルールの大部分を移植したもの）を、そのファイルだけにかける。Bandit 本体は PR 時に使う |
| 検査（Python 以外） | キット独自の簡易チェック（正規表現）。JavaScript・TypeScript（コマンドの実行、eval、画面への HTML の出力など）、Go、GitHub Actions のワークフロー（外から操作できる値の埋め込み、固定していない Action）、HTML を見る。コードのファイルだけを対象にし、文書のファイルには反応しない |
| 検査（全ファイル） | API の入口を書いたら「認可の確認」の助言を出す（3.12）。設定ファイル（CLAUDE.md、.mcp.json 等）の不審な記述（FR-26。未実装） |
| 除外の印 | Ruff の指摘は Ruff の印（`# noqa: 番号` と理由）、キット独自の簡易チェックと AI レビューの指摘は `security-kit:allow` と理由を、その行に書く |
| 絞り込み | 今回変えた行に重なる指摘だけを残す（3.2） |
| 結果の扱い | 検査ツールの結果をルール ID に変換し（4章）、重大度ごとに振り分ける。警告はすぐ Claude に通知、助言は記録だけして③のまとめに載せる |
| 通知のしかた | フックの結果として Claude に追加の情報を渡す（3.6 の型） |
| 重複を避ける | 同じファイル・同じ指摘は、このセッションで1回だけ通知する |

### 3.5 ③ 作業の区切りの検査

| 項目 | 内容 |
|---|---|
| 対象 | このターンで変更したファイル。②で記録したファイルに加え、git の変更一覧も見る（Claude が Bash で書き換えたファイルも拾うため） |
| 検査 | gitleaks（全ルール。書く前の判定で見つからない種類の秘密情報を拾う）、Semgrep（キットに同梱したルールを使い、ネットからは取得しない）、Trivy（Dockerfile・IaC が変更されている場合だけ） |
| 絞り込み | 今回変えた行に重なる指摘だけを残す（3.2）。Semgrep の「基準のコミットとの差だけを出す機能」は、未コミットの変更があると使えないため、ここでは使わない |
| 警告が残っているとき | Claude の応答を終わらせずに続けさせ、指摘の説明と修正を求める。無限に続かないよう、続けさせるのは1ターンに1回だけにする |
| 助言だけのとき | 応答は続けさせない。まとめに載せて、直すかどうかは利用者が決める。頼まれていない修正が増えるのを防ぐ |
| 直ったかの確認 | 伝えた警告が、変えたファイルにまだ残っているかを確かめ、「直した／未対応」を記録する（FR-44） |
| まとめの表示 | 最後に、このターンの指摘と対応状況（直した／未対応）、AI レビューの指摘、助言を、利用者向けに表示する（FR-19）。フックから利用者にメッセージを出す仕組み（systemMessage）を使う。ルールの名前と場所だけを書く |
| 対象ファイルが無いとき | 何もしない（ファイルを変更していない会話では動かない） |

### 3.6 Claude への通知文の型

フックから Claude に渡す通知は、毎回次の型にする。

```
[security-kit] 警告 R-012 SQL インジェクション
場所: app/db.py 42行目
何が危ないか: 入力された値をそのまま SQL 文につなげている
なぜ危ないか: 外部から SQL の命令を仕込まれ、データを盗まれたり消されたりする
どう直すか: プレースホルダー（? や :name）を使い、値は別に渡す
詳しく: /security-kit:consult R-012
→ 黙って直さず、利用者に「ひとこと：〜」の形で理由と直し方を伝えてから修正してください。除外の印は、利用者が認めたときだけ付けてください。
```

**守らせたい指示は、Skill ではなく通知文に入れる。** 試作で、通知を受けた Claude も、API を書くように頼まれた Claude も、senpai の Skill を読み込まなかった（試作の記録 10.3）。Skill は読まれないことがある前提で、次の指示は通知文そのものに入れる。

| 通知 | 通知文に入れる指示 |
|---|---|
| 警告 | 説明してから直す。除外の印は、利用者が認めたときだけ付ける |
| 止める | 書き込みは行われていない。Bash など別の方法で同じ内容を書かない。誤検知かどうかは利用者に確かめ、利用者が認めたときだけ印を付ける |
| 助言（認可の確認。3.12） | 他人のデータの ID で呼ばれたら何が止めるかを確かめ、気になる点を利用者に伝える。テストを提案する |

- 「何が危ないか／なぜ危ないか／どう直すか」は、ルールの YAML に書いた文章をそのまま使う（FR-13）。
- **通知文に入れてよいのは、ルールの文章、ファイル名、行番号だけとする。** 検査対象のコードやファイルの中身は入れない。中身に仕込まれた指示が Claude に伝わるのを防ぐため（NFR-13）。
- ルール ID が無い指摘（検査ツール側にだけあるルール）は、ツールの説明文を使い、重大度は「助言」とする。

### 3.7 Skill の構成

Skill は、フォルダ1つと `SKILL.md`（先頭に設定、その下に指示の文章）で作る。以前の「コマンド」は Skill に統合されているので、相談・報告・初期化も Skill として作る。

| Skill | 誰が呼ぶか | 主な設定 | 役割 | 該当要件 |
|---|---|---|---|---|
| senpai | Claude だけ | `user-invocable: false` | 伝え方の型、説明してから直す、してはいけないこと、認可の確かめ方とテストの例（`authz.md`）。ルールごとの説明・違反例・正常例（`rules/R-NNN.md`。build.py が生成） | FR-11〜13、FR-15 |
| consult | 利用者と Claude | `disallowed-tools`（書き換えの道具を外す）、`allowed-tools`（検査スクリプトだけを確認なしで動かす） | 相談コマンド（3.8） | FR-16 |
| report | 利用者だけ | `disable-model-invocation: true` | 報告コマンド（3.9） | FR-17 |
| init | 利用者だけ | `disable-model-invocation: true` | 初期化コマンド（9.3）。配布の設計とあわせて作る | FR-73 |

- ルールの説明は、独立した Skill にせず、senpai の資料として置く。通知を受けたときに使う点が senpai と同じで、Skill を分けると説明文（Skill の一覧に常に載る）が増えるだけのため。必要なルールの分だけ読ませる。
- `allowed-tools` は「確認なしで使ってよい道具」を足す設定で、ほかの道具を禁止するものではない（公式の説明で確認）。書き換えを禁止するには `disallowed-tools` を使う。
- consult の `allowed-tools` には、検査スクリプトの場所を `${CLAUDE_PLUGIN_ROOT}` で書く。これで、そのスクリプトだけが確認なしで動くことを実機で確かめた。広い指定（`Bash(python3 *)` など）は使わない。

- `description`（いつ使う Skill かの説明）は、Claude が使うかどうかを決める材料になる。「どんな頼み方のときに使うか」を具体的に書き、テストで確かめる（10章）。ただし、Claude が自分から Skill を読み込むとは限らない（3.6）。
- 本文は短くし、詳しい資料は別ファイルに分けて、必要なときだけ読ませる。
- 一般的なセキュリティの知識は、CodeGuard の公式プラグインに任せる（FR-03）。自社の Skill は、自社独自のルールと伝え方だけを持つ。
- 名前は、Claude Code 標準の `/security-review` や CodeGuard の Skill と重ならないようにする。

### 3.8 相談コマンド（FR-16）

| 項目 | 内容 |
|---|---|
| 呼び方 | `/security-kit:consult`（後ろに対象を書ける。例：ファイル名、ルール ID、「このログイン処理」） |
| 対象が無いとき | 今の変更（git の差分）を対象にする |
| 流れ | ①対象を決める ②検査スクリプトで③と同じ検査をかける ③関係するルール（自社分と CodeGuard）を読む ④認可の観点（誰がアクセスできるか）を確認する ⑤伝え方の型で答える |
| 検査スクリプト | `scripts/consult.py`。対象が無ければ、まだコミットしていない変更の、変えた行だけを見る。ファイルを名指しされたら、そのファイル全体を見る（以前からある問題も含める）。Ruff、簡易チェック、内蔵の秘密情報の判定、gitleaks をかけ、通知文の型で表示する。ファイルの中身は表示せず、書き換えず、記録も残さない |
| 書き換え | 相談では書き換えない。直すかどうかは利用者が決める。Skill の設定で、書き換えの道具（Write、Edit）を外す |
| 答えの最初 | 「大丈夫」「気になる点あり」「直した方がよい」のどれかを明示する |
| 答えの中身 | 検査ツールの指摘と、コードを読んで気づいた点を分けて書く。気づいた点には、どのくらい確かかを添える。最後に「直しましょうか？」と聞く |

### 3.9 報告コマンド（FR-17）

| 項目 | 内容 |
|---|---|
| 呼び方 | `/security-kit:report` |
| 報告の種類 | 誤った指摘／ルールの提案／使いにくい（遅い・邪魔など） |
| 流れ | 直前の指摘（ルール ID、場所）を自動で入れた下書きを作り、利用者が確認してから、キットのリポジトリに Issue として登録する |
| 下書きの材料 | `scripts/report.py` が、このセッションの直近の指摘（場面、重大度、ルール ID、検査ツールの番号、ファイルの種類）と、キットの版、報告先（plugin.json の `repository`）を表示する。ファイルの場所は出さない |
| 登録の前 | 下書きからコード、ファイルの場所、秘密情報、案件名・顧客名・人の名前、患者や利用者のデータを除き、利用者の了承を得てから登録する |
| 送らないもの | コードの中身や秘密情報は Issue に入れない。ルール ID、ファイルの種類、行数程度にとどめる。案件名・顧客名も書かない（キットのリポジトリは全案件で共有するため） |
| 前提 | GitHub CLI（gh）にログインしていること |

### 3.10 警告モード（FR-25）

- プロジェクトの設定ファイル（`.claude/security-kit.json`）で「警告モード」にすると、①の「止める」も止めずに「警告」として伝え、PR 時の判定も失敗にしない。
- 切り替えを環境変数ではなくファイルで行うのは、各自の PC と PR 時で同じ値を見るためである。このファイルの変更にはレビューが必須になる（FR-38）。
- パイロット運用（ステップ4）の既定は警告モードとする。
- 強制設定ファイル側の禁止（.env の読み取り、bypass の無効化）は、警告モードでも止める。これらはキットのフックではなく Claude Code 本体が止めるもので、誤検知がほぼ無いため。

### 3.11 例外と誤検知の扱い（FR-41、FR-46）

誤って止められたときに開発が止まらないよう、2つの逃げ道を用意する。

| 逃げ道 | 使う場面 | やり方 | 歯止め |
|---|---|---|---|
| 印による除外 | 検査ツールの誤検知（例：テスト用のダミーの鍵、安全だと確認済みの書き方） | 対象の行に、検査ツールごとの決まったコメント（印）を付ける。秘密情報は `.gitleaks.toml` にまとめて書くこともできる | 印の追加は PR の差分に出る。PR 時の判定が「今回増えた印」を一覧にしてコメントに載せ、承認者が確認する。`.gitleaks.toml` の変更はレビュー必須（FR-38） |
| 期限つきの例外 | ルールそのものを、ある範囲で一時的に外したい場合 | その案件の設定ファイル（`.claude/security-kit.json`）に「誰が・なぜ・いつまで・どの範囲」を書き、PR で承認を受ける | 期限が切れると自動的に無効になる。このファイルの変更はレビュー必須（FR-38）。案件の情報をキット側に溜めないよう、例外はその案件のリポジトリに置く |

- 印のコメントには理由を書く決まりにする（例：「テスト用のダミーの鍵」）。
- 止めたときの表示（3.3）と PR のコメント（6.3）には、この2つの方法と、次の手順への案内を必ず入れる。

**秘密情報が GitHub に上がってしまったとき（FR-46）**

1. その鍵をすぐ無効にして、作り直す。履歴から消すだけでは足りない（すでに読まれている前提で動く）。
2. ルール管理者に知らせる。
3. 無効にした後で、履歴からの削除を検討する。

この手順は方針書に載せ、PR のコメントから参照できるようにする。

### 3.12 認可の確認とテストの促し（FR-15）

認可の漏れ（他人のデータが見える）は検査ツールでは見つからないため、次の流れで補う。

1. ②の簡易チェックが、API の入口やデータベースへのアクセスを書いたことを検知する。
2. 「助言」として、次の2点を Claude に伝える。助言のうちこれだけは、作業のまとめに載せるのに加えて、その場で Claude にも伝える。作業は止めない。同じファイルについては、セッションで1回だけにする。
   - 誰がアクセスできるかを確認し、気になる点を利用者に一言伝える。
   - 他人のデータにアクセスできないことを確かめるテストを書くよう提案する。
3. 確認のしかたとテストの例は、senpai Skill の資料（`authz.md`）に書いておき、通知文にその場所を書く。

検知は「API やデータアクセスを書いた」という手がかりだけで、認可が正しいかどうかは判定しない。判定は人と AI のレビューに任せる（脅威モデル T-23）。

### 3.13 検査ツールが無い・失敗したとき

| 状況 | 先輩役の動き | 理由 |
|---|---|---|
| 検査ツールが入っていない | その検査を飛ばし、セッションで1回だけ「ツールが未導入」と助言する | 開発を止めないため。PR 時の検査が最後の砦になる |
| 検査ツールが時間切れ・エラー | その検査を飛ばし、記録に残す | 同上 |
| ①の検査 | 外部の検査ツールを使わないので、ツールが無くても働く | 「止める」はツールに依存させない |

### 3.14 AI レビュー（作業の区切りと、コミットの直後）

検査ツールでは見つからない問題（認可の漏れ、複数のファイルにまたがる問題など）を、AI に確かめさせる。どちらも背景で動き、利用者を待たせない。重大な指摘があったときだけ、Claude を呼び戻す。

| 項目 | 作業の区切りのレビュー | コミットの直後のレビュー |
|---|---|---|
| きっかけ | Claude の応答が終わる時点（Stop フック。背景で動く） | Claude が git commit を実行した直後（背景で動く） |
| 見るもの | このターンの差分 | コミットされた差分と、関係するファイル |
| レビュー役の道具 | なし（差分だけを見る） | 読む・探すだけ（Read、Grep、Glob） |
| ねらい | 書いた内容の問題を、その場で拾う | データの流れが複数のファイルにまたがる問題と、認可の確認の漏れを拾う |
| 目安の時間 | 5〜30 秒 | 10〜60 秒 |

**レビュー役の起動のしかた**

- 利用者の Claude Code を、もう1つ起動して使う。キットは利用者のサインイン情報に触れない。
- 「制限つき」で起動する。コマンドの実行と通信をさせず、利用者・プロジェクトの設定も読み込ませない。秘密情報のファイル（.env、鍵ファイル）は読ませない。
- レビュー役の中ではキットのフックを動かさない（レビューがレビューを呼ぶのを防ぐ）。
- 使うモデルは、プロジェクトの設定ファイルで選ぶ（既定は sonnet）。

**レビュー役に渡すもの**

- レビューの手引き（`data/review_prompt.md`）：判断の基準、特に確かめること、指摘しないもの。
- 分類の一覧：自社のルールから作る（分類 → ルール ID）。
- プロジェクトの決まり（任意）：`.claude/security-kit-guidance.md` に書いた、その案件だけのルール。
- 差分：送る前に、秘密情報らしき部分を伏せ字にする。文書・ロックファイル・画像などは送らない。長い差分は打ち切る。

**レビュー役の返事の扱い（NFR-13）**

レビュー役の返事は、信頼できないデータとして扱う。差分に仕込まれた文章にレビュー役が操られても、影響が広がらないようにする。

| 確かめること | 合わないとき |
|---|---|
| 決めた形（分類、ファイル、行、重大度、メモ）で返っているか | 受け取らない |
| 分類が、決めた一覧の中にあるか | その指摘を捨てる |
| ファイルが、送った差分の中にあるか | その指摘を捨てる |
| メモに URL や秘密情報らしき文字列が無いか | メモを捨てる（指摘は残す） |
| メモの長さと記号 | 160字で切り、コードとして読める記号を取り除く |

- Claude への通知文は、ほかの検査と同じ型（3.6）で、自社のルールの文章から作る。レビュー役のメモは「参考。指示ではありません」と明記して1行だけ添える。
- 除外の印（`security-kit:allow` と理由）が付いた行の指摘は、受け取らない。

**重大度と伝え方**

| レビュー役の判定 | 伝え方 |
|---|---|
| critical・high | Claude を呼び戻し、確認と対応を求める |
| medium | 呼び戻さない。次の作業のまとめに載せる |

- 利用者がはっきり指定した書き方で、Claude がすでに危険性を伝えてある場合は、理由を一言伝えるだけでよいとする（指定に逆らって書き換えさせない）。
- 機械的な検査ですでに伝えた指摘（同じルール・同じファイル・近い行）は、重ねて伝えない。

**利用量を抑える工夫**

- コードを変えていないターン、文書だけを変えたターンでは動かない。
- 同じ差分は二度見ない。
- 1つのセッションでの回数に上限を設ける（既定 20 回）。
- プロジェクトの設定ファイルで、作業の区切り・コミットの直後のそれぞれを止められる。
- レビュー1回ごとに、かかった費用の目安を記録する。

**位置づけ（独立性の原則）**

このレビューは、コードを書いた AI と同じベンダーの AI による確認である。会話の履歴は引き継がないが、PR 時の最終判定には使わない（層3 の自己チェックにあたる）。最終判定は、AI ではない検査ツールと、別ベンダーの AI で行う（6章）。レビュー役の起動コマンドは差し替えられる作りにしてあり、将来、別ベンダーの AI を手元でも使える。

### 3.15 公式プラグインとの関係

Anthropic 公式の `security-guidance` プラグイン（Apache-2.0）と同じ役割を、キットだけで受け持つ。公式プラグインの考え方を参考にし、コードは流用していない。

| 役割 | 公式プラグイン | キット |
|---|---|---|
| 書いた直後の注意 | 約25種類の正規表現。文書のファイルにも反応することがある | Python は Ruff（コードの構造を見るので誤りが少ない）。それ以外は独自の簡易チェック。コードのファイルだけを見る。このターンで変えた行に絞る |
| 作業の区切りの AI レビュー | あり（背景で動く） | あり（背景で動く）。3.14 |
| コミット時の AI レビュー | あり（関係するファイルをたどる） | あり（関係するファイルをたどる）。3.14 |
| 組織のルールを AI に読ませる | 手で書いたファイル | 自社のルール（YAML）から自動で渡す。案件だけの決まりは別ファイル |
| 秘密情報を書く前に止める | 無い（注意するだけ） | あり（3.3） |
| 説明の型とルール ID | 英語の注意文 | 初心者向けの日本語の型（何が／なぜ／どう直すか）とルール ID |
| 直ったかの確認とまとめ | 無い | あり（3.5） |
| 記録と集計 | 動作の記録のみ | 指摘と結果の記録、集計（7章） |
| AI の返事の扱い | AI が書いた文章を Claude に渡す | 決めた形だけを受け取り、自社のルールの文章で伝える（3.14） |
| サインイン情報 | Claude Code から受け取って使う | 触れない |

- 両方を入れると同じ書き込みに注意が2つ出るので、キットを使うプロジェクトでは公式プラグインを止める。初期化コマンドが、プロジェクトの設定にその指定を入れる（2.3）。
- 公式プラグインが更新されたときは、検出する書き方とレビューの観点に取り込むべきものが無いかを、四半期の見直しで確かめる。

## 4. ルールと検査ツールの対応付け

### 4.1 データの流れ

```
 rules/*.yaml（人が編集する唯一の元データ）
      │
      ▼ build.py
      ├─▶ plugins/security-kit/data/rules.json          フックが読むルールデータ（作成済み）
      ├─▶ plugins/security-kit/skills/senpai/rules/   ルールごとの説明（作成済み）
      ├─▶ tests/rules/examples.json                    違反例と正常例（ルールのテストが読む。作成済み）
      ├─▶ templates/CLAUDE.md の追記部分               （未作成）
      ├─▶ templates/settings.json の禁止ルール         （未作成。安全装置の設計とあわせて）
      ├─▶ AGENTS.md（別ベンダー AI のレビュー基準）    （未作成）
      └─▶ 方針書（社内向け）、一覧表（CSV）           （未作成）
```

- フックは YAML を直接読まず、build.py が作る JSON を読む。Python の標準ライブラリには YAML の読み込み機能が無いため。
- 違反例と正常例も JSON に書き出し、ルールのテストはそれを読む。テストを追加のインストールなしで動かすため（10章）。
- 生成物はリポジトリに入れる（プラグインとして配布するため）。元の YAML とずれないよう、キットの CI で「生成し直しても差が出ないこと」を検査する（FR-04）。

### 4.2 対応付けのしかた

検査ツールはそれぞれ独自のルール番号を持つ。ルールの YAML に「どのツールのどの番号が、このルールにあたるか」を書いておき、検査結果を自社のルール ID と重大度に変換する（FR-03）。

| 自社ルール | 重大度 | 対応する検査ツールの番号（例） |
|---|---|---|
| R-001 秘密情報の直書き | 止める | キット内蔵の判定（書く前）、gitleaks の全ルール（作業の区切り・コミット前・PR 時） |
| R-0xx パスワードらしき値の直書き | 警告 | Ruff S105・S106・S107。変数の名前からの当て推量なので、「止める」の R-001 には対応付けない |
| R-0xx SQL インジェクション | 警告 | Ruff S608、Semgrep の SQL インジェクション系ルール |
| R-0xx 認可の確認 | 助言 | キット独自の簡易チェック |

- 対応付けの無い指摘は、ツールの説明文で伝え、重大度は「助言」にする。
- ルールの YAML の項目（FR-02）の詳細は、データ設計書で定める。

### 4.3 Semgrep のルールの持ち方（FR-51）

- 使うルールを選んで、プラグインの `semgrep-rules/` に同梱する。実行のたびにネットから取得しない。
- 理由：バージョンを固定できる。起動が速くなる。通信を制限した環境でも動く。利用状況が外部に送られない。
- 同梱してよいかは、ルールの利用条件を確認してから決める 【要確認】。同梱できない場合は、自社で書いたルールだけを使い、公開ルールは PR 時だけにする。

### 4.4 build.py の動かし方

| 項目 | 内容 |
|---|---|
| 実行 | `uv run --locked build/build.py`（生成する）、`uv run --locked build/build.py --check`（生成し直して差が出ないかを確かめる。CI で使う） |
| 使うライブラリ | YAML の読み込みに PyYAML だけを使う。スクリプトの先頭に必要なライブラリを書き（PEP 723）、`build/build.py.lock` に版とハッシュを固定する。`--locked` を付けると、固定した内容と違うものは入らない |
| cooldown | ライブラリを選び直すときも、決めた日付（`exclude-newer`）より後に公開された版は使わない。更新するときは日付を進めてから固定し直し、PR でレビューする |
| 安全な読み込み | YAML は安全な読み込み方（SafeLoader の派生）で読む。同じ項目を2回書いたら誤りにする（標準では後の値で黙って上書きされるため） |
| 生成前の検査 | データ設計書 3.7 の検査に加え、知らない項目、正規表現の誤り、簡易チェックの番号の重複を誤りにする。誤りがあれば何も生成しない |
| 生成物 | 4.1 の「作成済み」のもの。作成日時は入れない（同じ元データからは同じ結果） |
| uv が無いとき | 生成物はリポジトリに入っているので、ルールを変えない人は uv が無くてもキットを使える。ルールを変える人だけが uv を入れる |

## 6. PR 時の最終チェック

### 6.1 構成

検査の中身はキットのリポジトリの「共通ワークフロー」に置き、各プロジェクトはそれを呼び出すだけにする（FR-34）。

```
 各プロジェクト                               キットのリポジトリ
 .github/workflows/security.yml              .github/workflows/security-check.yml
 （数行。呼び出すだけ）     ──呼び出し──▶     （検査の中身）
                          コミット SHA で固定
```

- 呼び出しはタグではなくコミット SHA で固定する（FR-35）。キットを更新したときは、Dependabot が各プロジェクトに更新の PR を作る。
- 非公開リポジトリの共通ワークフローを別の非公開リポジトリから呼べるよう、キットのリポジトリの Actions のアクセス設定を変更する。Dependabot が非公開のキットのリポジトリを読めるかも含めて確認する 【要確認：実機で確認する】。

### 6.2 検査の内容（層1。FR-30）

検査は並列に動かす。

| ジョブ | 検査ツール | 対象 |
|---|---|---|
| コード | Semgrep（OWASP 対応ルール）、Bandit | Python のコード |
| 秘密情報 | gitleaks | PR に含まれる全コミット |
| 依存ライブラリ | pip-audit、osv-scanner | ロックファイル（間接的な依存と悪性パッケージ情報を含む） |
| 構成ファイル | Trivy | Dockerfile、IaC |
| ワークフロー | zizmor | `.github/workflows/` |
| キット導入確認 | キット独自のスクリプト | `.claude/settings.json` にキットの設定があるか、バージョンが古くないか（FR-33） |
| 判定とコメント | キット独自のスクリプト | 上の結果を集めて判定する（6.3） |

### 6.3 判定と PR へのコメント

**判定の対象は、今回の PR で増えた指摘だけにする（FR-39）。**

| 検査 | 今回の PR で増えた指摘の求め方 | 以前からある指摘 |
|---|---|---|
| コード（Semgrep） | 「基準のコミット（取り込み先のブランチ）に無かった指摘だけを出す」機能を使う | 件数だけをコメントに載せる。判定には使わない |
| コード（Bandit）、構成ファイル、ワークフロー | PR で変えた行に重なる指摘だけを残す | 同上 |
| 秘密情報 | PR に含まれるコミットだけを検査する | 対象にしない |
| 依存ライブラリ | PR で追加・更新したライブラリの指摘 | 既知の脆弱性は警告として載せる。悪性パッケージは以前からあるものも失敗にする |

| 項目 | 内容 |
|---|---|
| 変換 | 各ツールの結果を、4章の対応付けで自社のルール ID と重大度に変換する |
| 判定 | 今回増えた「止める」の指摘が1件でもあれば失敗にする。警告・助言だけなら成功にする。警告モードでは失敗にしない |
| コメント | PR に1件のコメントを書き、内容は更新していく。重大度ごとに、伝え方の型（3.6）で日本語で書く。通知文と同じく、コードの中身は載せない |
| 増えた印の一覧 | 今回の PR で増えた「問題ない」の印（3.11）を一覧にしてコメントに載せ、承認者が確認できるようにする |
| マージの条件 | GitHub のブランチ保護で、「判定」ジョブの成功と、承認者1名のレビューを必須にする（GitHub の有料プランが前提） |
| 記録 | 結果を JSON にまとめ、ワークフローの成果物として保存する（7章） |

### 6.4 CI 自体の防御（FR-35〜38）

| 対策 | 内容 | 備える脅威 |
|---|---|---|
| バージョンの固定 | Action はコミット SHA、検査ツールはバージョンとチェックサムで固定する | 検査ツールや Action の乗っ取り |
| 最小権限 | ワークフローの既定の権限は読み取りだけにする。PR へのコメントを書くジョブだけに、コメントの書き込み権限を与える | 同上 |
| 検査に秘密情報を渡さない | 検査ジョブには秘密情報を一切渡さない | 同上 |
| 長く使える秘密情報を置かない | リポジトリの Actions に、長く使える秘密情報を登録しない。デプロイ用などで必要な場合は、main ブランチでしか使えない置き場（Environments）に入れる 【要確認：プランの条件】 | アカウントが乗っ取られ、ブランチに悪性のワークフローを足される |
| 変更のレビュー必須 | `.github/workflows/`、`.claude/`、`.gitleaks.toml`、`.pre-commit-config.yaml` の変更は、CODEOWNERS で承認者のレビューを必須にする | 同上、および設定の改ざん |
| 起動のしかた | 外部の人が出した PR でも秘密情報と書き込み権限を持って動く起動方法（pull_request_target）は使わない | 外部からの PR の悪用 |
| 更新の cooldown | Dependabot による Action・ツールの更新は、公開から7日たったものだけにする（FR-51） | 乗っ取られた直後の版の取り込み |

- ブランチ保護は main への取り込みを守るが、ブランチ上で動くワークフローは止められない。そのため「盗まれて困るものを置かない」を基本にする。
- アカウントの乗っ取りそのものは、全メンバーの2要素認証で防ぐ（FR-75）。

### 6.5 層2・層3

| 層 | 実現方法 | 備考 |
|---|---|---|
| 層2：別ベンダー AI（FR-31） | OpenAI Codex の GitHub 連携機能を、リポジトリ側で有効にする。レビュー基準は `AGENTS.md`（build.py が生成） | GitHub Actions の外で動くので、CI に秘密情報を置かずに済む（FR-36）。契約が決まってから導入する |
| 層3：自己チェック（FR-32） | 利用者が Claude Code の `/security-review` を実行する。CLAUDE.md の追記で、書き終わったら実行するよう促す | 最終判定には使わない |

## 7. 記録（FR-40〜45）

| 記録 | 置き場所 | 中身 | 位置づけ |
|---|---|---|---|
| PR 時の結果 | PR へのコメント、ワークフローの成果物（JSON） | ルール ID、日時、ファイル、重大度、判定 | **正**とする記録 |
| 先輩役の記録 | 各自の PC（ユーザーのフォルダ内。リポジトリには入れない） | ルール ID、日時、ファイル、重大度、結果（直した／未対応） | 補助 |
| Claude Code の標準記録 | OpenTelemetry で出力（FR-45） | フックによるブロック、権限の判定 | 補助。第一弾では任意 |

- **「直した／未対応」の判定（FR-44）**：同じ指摘が次の検査（③または PR 時）で消えていれば「直した」、残っていれば「未対応」とする。
- **長期保存（FR-43）**：ワークフローの成果物は保存期間に上限があるため、週1回の集計ジョブで集計結果をキットのリポジトリに保存する方式を候補とする。各プロジェクトの結果を読む権限の扱いを含め、詳細設計で決める 【要確認】。
- **集計の単位**：チーム単位で集計し、個人名は集計結果に出さない（NFR-12）。
- **記録にも、コードの中身や秘密情報は入れない。**

## 8. 安全装置（概要。次版で詳しく書く）

| 部品 | 置き場所 | 中身 | 該当要件 |
|---|---|---|---|
| 強制設定ファイル | 各自の PC（`/etc/claude-code/managed-settings.json`） | 緩めない「止める」ルールだけを書く。.env・鍵ファイル・AI ツールの認証ファイルの読み取り禁止、sudo の禁止、bypass の無効化、MCP サーバー・プラグインの許可リスト | FR-20、FR-27、FR-29、FR-72 |
| リポジトリの設定 | 各プロジェクトの `.claude/settings.json` | 調整しうる設定。プラグインの有効化、サンドボックス、プロジェクト固有の禁止 | FR-21、FR-74 |
| パッケージ導入前チェック | プラグインのフック（Bash の実行前） | pip・uv・poetry・uvx・pipx・npx の実行を検知し、OSV と公開日を確認する。フックの `if` 条件を使い、該当するコマンドのときだけスクリプトを起動する（それ以外の Bash では起動しない） | FR-22 |
| cooldown とロックファイル | 各プロジェクトの `pyproject.toml`、`.npmrc` | 公開から7日未満の版を入れない設定。npm ではインストール時スクリプトも無効にする。人がターミナルで直接実行した場合にも効く | FR-23 |
| 利用者の設定の変化の検知 | プラグインのフック（セッションの開始時） | `~/.claude/settings.json` などのフックや MCP の接続先が、前回から変わっていたら知らせる | FR-26 |
| 管理されたフックだけを動かす設定 | 強制設定ファイル | 利用者の設定に仕込まれたフックを動かさない。利用者が自分で入れたフックも止まるため、パイロットで影響を確かめてから採用を決める 【要確認：キットのフックが動き続けるかを実機で確認する】 | FR-76 |

- 強制設定ファイルには、変える必要の無いものだけを書く。中身を変えると全員が sudo でセットアップをやり直すことになるため、調整しうる設定はリポジトリの設定とプラグインに置く。
- 各自の PC の記録と状態は、Claude Code がプラグインごとに用意するデータ置き場（`~/.claude/plugins/data/` の下）に置く（試作で確認済み）。
- bypass の無効化は通知なしで効く（実機で確認済み）。セットアップ時の案内と方針書で周知する（FR-29）。

2. 一度だけ全体を検査し、既存の指摘の一覧を作る（FR-39）。

## 10. テスト（NFR-06、NFR-07）

| テスト | 確かめること | いつ動かすか | AI を使うか |
|---|---|---|---|
| ルールのテスト | 各ルールの違反例で指摘が出ること、正常例で出ないこと。AI レビューだけで見つけるルールは対象外。秘密情報のルールの違反例は、ファイルに完成形の鍵を書けないため、フックのテストで実行時に組み立てて確かめる | キットの変更のたび | 使わない |
| フックのテスト | 「この入力ならこの出力（止める／通知文／何もしない）」になること。変えた行だけに絞れていること | キットの変更のたび | 使わない |
| すり抜けテスト | 既知の回避手口（サブプロセス経由の読み取り、環境変数、コマンドの連結、uvx・npx 経由の導入など）を止められること | キットの変更のたび（強制設定とサンドボックスの分はリリース前に実機で） | 一部使う |
| 生成物のずれの検査 | build.py で生成し直しても差が出ないこと（4.1、4.4） | キットの変更のたび | 使わない |
| コマンドのテスト | 相談・報告のスクリプトが、ファイルの中身や場所を出さないこと、書き換えないこと | キットの変更のたび | 使わない |
| 書式の検査 | プラグインと Skill の書式に誤りが無いこと（`claude plugin validate`） | キットの変更のたび | 使わない |
| ふるまいのテスト | Skill が狙った頼み方で使われること、通知を受けた Claude が説明してから直すこと（`claude plugin eval`） | リリース前 | 使う（利用量がかかる） |

- フックのテストは Python の標準のテスト機能で書き、追加のインストールなしで動くようにする。
- AI を使うテストは利用量がかかるため、リリース前だけにする。
- AI レビューの仕組み（差分の準備、返事の確認、通知文、二度見ないこと）は、決まった返事をする代役に差し替えて、AI を呼ばずにテストする。

## 11. 性能の見積もり（NFR-01）

| タイミング | 主な処理 | 見積もり | 目標 |
|---|---|---|---|
| ① 書く前 | Python の起動、内蔵の判定 | 約 0.08 秒（実測） | 1 秒以内 |
| ② 書いた直後 | Python の起動、Ruff（1ファイル）、簡易チェック、変更行の絞り込み | 約 0.13 秒（実測） | 2 秒以内 |
| ③ 作業の区切り | gitleaks、Semgrep（変更ファイルのみ）、Trivy（必要時） | 未計測（gitleaks は約 1.5 秒） | 30 秒以内 |

**実測した値（2026-11-13、WSL2、Python 3.12）**

| 測ったもの | 時間 |
|---|---|
| Python のフックを模したもの（起動、入力の読み込み、正規表現20本） | 約 0.06 秒 |
| Python に検査ツール呼び出し用の部品を読み込ませた起動 | 約 0.08 秒 |
| Ruff 単体（300行のファイル1つ） | 約 0.02 秒 |
| gitleaks 単体（標準入力） | 約 1.4 秒（起動だけで約 1 秒） |
| AI レビュー（作業の区切り。小さな差分、haiku） | 約 6 秒（背景で動くので待たせない） |
| AI レビュー（コミットの直後。小さな差分、haiku） | 約 11 秒（背景で動くので待たせない） |

- Python の分は、目標の2秒に対して3〜4%である。フックの言語を変える必要は無い。最初の1回だけは 0.1〜0.2 秒かかった。
- Ruff は十分に速い。gitleaks は起動が遅いため、①では使わない（3.3）。Semgrep と Trivy は未計測で、③の試作で測る。
- 詳しい実測値は、試作の記録（docs/design/prototype-notes.md）にある。
- Semgrep は起動に数秒かかるため、②には入れない。③で収まらない場合は、ルールを絞るか、PR 時だけに回す。
- 速くする工夫は、言語の変更より次を優先する。不要な起動を減らす（フックの `if` 条件）、1回の起動で検査をまとめる、Semgrep のルールを絞って同梱する。
- フックには時間切れの上限を設定し、上限を超えたら検査を飛ばす（3.13）。
