## 1. この文書について

キットが扱うデータの形と置き場所を決める。対象は次の7種類である。

| データ | 何に使うか | 章 |
|---|---|---|
| ルール | セキュリティの観点の元データ。人が編集する | 3章 |
| 例外 | ルールを一時的に外す記録 | 4章 |
| ルールデータ | フックが読む、ルールの生成物 | 5章 |
| プロジェクトの設定 | プロジェクトごとのキットの動かし方 | 6章 |
| セッションの状態 | 同じ指摘を繰り返さないための一時的な記憶 | 7章 |
| 記録 | 指摘とその結果の履歴 | 8章 |
| 集計 | 成功指標を出すための数字 | 9章 |

### 設計の決まり

| 決まり | 内容 |
|---|---|
| ルールは YAML で書く | 人が編集するルールは YAML で書き、ほかの文書や設定はそこから自動で作る（FR-01） |
| プログラムが読むのは JSON | フックと PR の判定は JSON を読む。Python の標準機能だけで読めるため。プロジェクトの設定と例外は、フックが直接読むので JSON で書く |
| 案件の情報をキット側に溜めない | キットのリポジトリは全案件で共有する。入れるのは、どの案件にも当てはまる形にしたルールと、件数だけにする。案件名・顧客名・実際のデータは入れない。案件ごとの情報は、その案件のリポジトリの中に置く |
| 患者データは保存しない | キットは患者データを保存しない。検査の記録にも、患者の情報が入り込まないようにする（8.1） |
| コードの中身を入れない | 記録・通知・集計のどれにも、検査対象のコードやファイルの中身、秘密情報そのものを入れない（NFR-13） |
| 個人を特定する情報を入れない | 記録と集計に、氏名・メールアドレス・PC のユーザー名を入れない。ファイルの場所はリポジトリからの相対パスで書く（NFR-12） |
| 時刻で差が出ないようにする | 生成物に作成日時を入れない。同じ元データからは、いつ作っても同じ結果になるようにする（FR-04 のずれの検査のため） |

## 2. データの置き場所と保存期間

| データ | 形式 | 置き場所 | git に入れるか | 保存期間 |
|---|---|---|---|---|
| ルール | YAML | キットの `rules/R-NNN.yaml`（1ルール1ファイル） | 入れる | 残し続ける（変更履歴が証跡になる） |
| 例外 | JSON | 各プロジェクトの `.claude/security-kit.json` の中 | 入れる | 残し続ける（期限切れも消さない） |
| ルールデータ | JSON | プラグインの `data/rules.json` | 入れる（生成物） | ― |
| プロジェクトの設定 | JSON | 各プロジェクトの `.claude/security-kit.json` | 入れる | ― |
| セッションの状態 | JSON | 各自の PC | 入れない | 7日で消す |
| 先輩役の記録 | JSON Lines | 各自の PC | 入れない | 90日で消す（溜まり続けないための既定値） |
| PR 時の結果 | JSON | GitHub Actions の成果物 | 入れない | GitHub の保存期間（既定90日） |
| 集計 | JSON | キットの `metrics/` | 入れる | 消さない（小さなファイルで、git に残り続ける。FR-43） |

- 各自の PC での置き場所は、Claude Code がプラグイン用に用意するデータ置き場があればそれを使い、無ければユーザーのフォルダ内（例：`~/.local/state/security-kit/`）に置く 【要確認：試作で確認する】。
- JSON Lines は、1行に1件ずつ JSON を書く形式である。追記が速く、途中で壊れても他の行は読める。

**保存期間の考え方**

- 要件で保存期間を定める必要があるのは、正とする記録だけである（FR-43）。集計を git に入れて消さない形にしたので、第一弾で期間を決める必要は無い。
- PR 時の結果（成果物）は GitHub の保存期間で消えるが、必要な数字は集計に残る。
- 各自の PC の記録の90日は、要件ではなく、ファイルが溜まり続けないための既定値である。
- ここでいう記録は、検査の記録（どのルールの指摘が、いつ、どこに出たか）である。患者データそのものではない。
- 患者データを扱う案件では、検査の記録の保存期間が、顧客との契約や医療情報のガイドラインで決まる可能性がある。Lv2 の設計で確認する。

## 3. ルール（rules/R-NNN.yaml）

### 3.1 ルールの種類

| 種類 | 値 | 意味 | 持つ項目 |
|---|---|---|---|
| 自社独自 | `own` | 当社が決めたルール | すべての項目 |
| 対応付け | `mapped` | 公開の標準（CodeGuard、OWASP 等）にあるルール。本文は書き写さず、検査ツールとの対応だけを持つ（FR-03） | 一部の項目 |

- ID は種類に関係なく `R-` と3桁の連番にする（例：R-001）。使わなくなった番号は再利用しない。
- どちらにも当てはまらない検査ツールの指摘は、ツールの説明文で伝え、重大度は「助言」にする（基本設計書 3.6）。

### 3.2 項目

| 項目 | 自社独自 | 対応付け | 意味 | 値の例 |
|---|---|---|---|---|
| `id` | 必須 | 必須 | ルール ID | `R-012` |
| `name` | 必須 | 必須 | 名称 | `SQL インジェクション` |
| `kind` | 必須 | 必須 | 種類 | `own` / `mapped` |
| `severity` | 必須 | 必須 | 重大度 | `block`（止める）/ `warn`（警告）/ `advise`（助言） |
| `level` | 必須 | 必須 | 適用する段階 | `1`（第一弾）/ `2`（強化版） |
| `domain` | 必須 | 必須 | 領域 | `code` / `api` / `ai` / `dependency` / `secret` / `config` / `workflow` / `data` |
| `status` | 必須 | 必須 | 状態 | `active`（有効）/ `draft`（準備中）/ `retired`（廃止） |
| `references` | 必須 | 必須 | 根拠（標準の名前と番号） | 下の例を参照 |
| `message.what` | 必須 | 任意 | 何が危ないか（1文） | |
| `message.why` | 必須 | 任意 | なぜ危ないか（1文） | |
| `message.fix` | 必須 | 任意 | どう直すか（1文） | |
| `examples` | 必須 | ― | 違反例と正常例。テストを兼ねる（3.4） | |
| `detection` | 必須 | 必須 | 検出方法（3.3） | |
| `confidence` | 必須 | 必須 | 検出の確実性 | `high` / `medium` / `low` |
| `owner` | 必須 | 必須 | 担当者（GitHub の ID） | |
| `last_reviewed` | 必須 | 必須 | 最終見直し日 | `2026-11-13` |
| `feedback_applied` | 任意 | 任意 | 繰り返す指摘を CLAUDE.md などへ反映した日。再発率の計算に使う（FR-56） | `2026-12-01` |

- `message` の3つの文は、Claude への通知文にそのまま使う（基本設計書 3.6）。初心者にもわかる日本語で、1文ずつ書く。
- 対応付けのルールでも、`message` の短い文は自社で書いてよい。詳しい説明や例は書き写さず、`references` で参照先を示す。`message` が無ければ、検査ツールの説明文を使う。
- 「止める」にするルールは、`confidence` が `high` のものに限る（誤検知がほぼ無いものだけを止める方針のため）。

### 3.3 検出方法（detection）

1つのルールに、複数の検出方法を書ける。

| `tool` の値 | 意味 | あわせて書く項目 |
|---|---|---|
| `gitleaks` / `ruff` / `semgrep` / `bandit` / `trivy` / `osv` / `zizmor` | その検査ツールで検出する | `ids`：そのツールでのルール番号の一覧。`"*"` はそのツールの全ルール |
| `kit` | キット独自の簡易チェック（正規表現） | `pattern`：正規表現。`files`：対象のファイル名の形 |
| `settings` | Claude Code の設定で止める | `deny`：禁止ルールの一覧 |
| `process` | 機械では検出できず、運用で守る | `note`：守り方の説明 |

- `process` を書くことで、「このルールは技術だけでは止められない」ことをルール自体に明記する（NFR-03）。

### 3.4 違反例と正常例（examples）

- `bad`（違反例）と `good`（正常例）を書く。それぞれ、ファイル名と中身を持つ。
- **この例がそのままテストになる。** キットの CI が、違反例で指摘が出ること、正常例で指摘が出ないことを確かめる（NFR-06）。
- そのため、ルール1件の追加は YAML ファイル1つの追加で済む（NFR-09）。複数のファイルが必要な複雑なテストだけ、`tests/` に別に書く。
- 違反例に本物の秘密情報を書かない。秘密情報のルールでは、形だけ合わせたダミーを使う。
- ルールの説明と例に、案件名・顧客名・実際のデータを書かない。案件で気づいたことをルールにするときは、どの案件にも当てはまる形にして書く。

### 3.5 例：自社独自のルール（警告）

```yaml
id: R-012                  # 番号は例
name: SQL インジェクション
kind: own
severity: warn
level: 1
domain: code
status: active
references:
  - "OWASP Top 10:2025 インジェクション"
message:
  what: 入力された値をそのまま SQL 文につなげている
  why: 外部から SQL の命令を仕込まれ、データを盗まれたり消されたりする
  fix: プレースホルダー（? や :name）を使い、値は別に渡す
examples:
  bad:
    - file: app.py
      code: |
        def find(cur, user_id):
            cur.execute(f"SELECT * FROM users WHERE id = {user_id}")
  good:
    - file: app.py
      code: |
        def find(cur, user_id):
            cur.execute("SELECT * FROM users WHERE id = ?", (user_id,))
detection:
  - tool: ruff
    ids: [S608]
confidence: medium
owner: monigairu
last_reviewed: 2026-11-13
```

### 3.6 例：設定と運用で守るルール（止める）

```yaml
id: R-005
name: 患者データ・本番データを AI や外部サービスに渡さない
kind: own
severity: block
level: 1
domain: data
status: active
references:
  - "要件定義書 11章 R-005"
message:
  what: 患者データや本番データを読もうとしている
  why: AI や外部サービスに渡ると、法令上・信頼上の影響が最も大きい
  fix: 開発にはダミーのデータを使う
examples:
  bad: []
  good: []
detection:
  - tool: settings
    deny:
      - "Read(**/*.dcm)"          # 書き方は詳細設計で確認する
  - tool: process
    note: 患者データ・本番データを開発機とリポジトリに置かない
  - tool: process
    note: データ区分のルールに従う（要件定義書 12章）
confidence: high
owner: monigairu
last_reviewed: 2026-11-13
```

- 設定で止めるルールの例は、すり抜けテスト（NFR-07）で確かめる。`examples` は空でよい。

### 3.7 build.py による検査

build.py は、生成の前に次を検査し、問題があれば失敗する。

- 必須の項目がそろっているか。値が決められた選択肢の中にあるか。
- ID が重複していないか。ファイル名と ID が合っているか。
- 同じ検査ツールの同じ番号が、2つのルールに対応付けられていないか。
- 「止める」のルールの `confidence` が `high` か。
- 最終見直し日から6か月を過ぎたルールがあれば警告する（FR-53）。

YAML を読むのは build.py だけである。YAML を読むための追加ライブラリは、バージョンを固定し、安全な読み込み方だけを使う。フックには追加ライブラリを使わない（基本設計書 1.3）。

## 4. 例外（各プロジェクトの .claude/security-kit.json の中）

ルールそのものを、ある範囲で一時的に外すための記録である（FR-41）。検査ツールの誤検知を1行だけ除外する「印」は、ここには書かない（基本設計書 3.11）。

例外は、キットのリポジトリではなく、その案件のリポジトリに置く。理由は2つある。

- 案件の情報（何を、なぜ認めたか）を、全案件で共有するキット側に溜めないため。
- 例外を足すたびにキットを作り直して配り直さなくて済むようにするため。

### 4.1 項目

| 項目 | 必須 | 意味 |
|---|---|---|
| `id` | 必須 | 例外の番号。`EX-` と年と連番（例：EX-2026-001） |
| `rule` | 必須 | 対象のルール ID |
| `paths` | 任意 | 対象のファイルやフォルダ。無ければリポジトリ全体 |
| `detail` | 必須 | 何を認めるか |
| `reason` | 必須 | なぜ必要か |
| `requested_by` | 必須 | 申請した人（GitHub の ID） |
| `approved_by` | 必須 | 承認した人（GitHub の ID） |
| `created` | 必須 | 作成日 |
| `expires` | 必須 | 期限。作成日から90日以内（実質的に無期限の例外を作らせないための既定値。延ばすときは作り直す） |

### 4.2 例

プロジェクトの設定ファイル（6章）の `exceptions` に書く。

```json
{
  "exceptions": [
    {
      "id": "EX-2026-001",
      "rule": "R-004",
      "paths": ["pyproject.toml"],
      "detail": "パッケージ foo の 1.2.3（公開から3日）を入れる",
      "reason": "重大な脆弱性の修正版のため、7日待たずに入れる",
      "requested_by": "monigairu",
      "approved_by": "example-approver",
      "created": "2026-11-13",
      "expires": "2026-11-20"
    }
  ]
}
```

### 4.3 決まり

- 例外の追加は、その案件の PR で行い、承認者のレビューを必須にする（FR-38）。
- PR 時の検査が、必須の項目がそろっているかと、期限が上限を超えていないかを確かめる。
- 期限が切れた例外は、フックと PR の判定が実行時に日付を見て無効として扱う。
- 週ごとの集計には、有効な例外の件数だけを入れる。内容や案件名は入れない。
- 期限切れの例外は消さずに残す。証跡になる（目的4）。
- 患者データのルール（R-005）は、例外の対象にできない。

## 5. ルールデータ（data/rules.json）

build.py が、ルールから作る。フックと PR の判定が読む。案件ごとの情報（例外など）は含めない。

### 5.1 例

```json
{
  "schema_version": 1,
  "kit_version": "0.1.0",
  "rules": {
    "R-001": {
      "name": "秘密情報をコードに直接書かない",
      "severity": "block",
      "what": "API キーやパスワードをコードに直接書いている",
      "why": "コードが共有されると、その鍵で不正に利用される",
      "fix": "環境変数や秘密情報の管理の仕組みから読み込む"
    },
    "R-012": {
      "name": "SQL インジェクション",
      "severity": "warn",
      "what": "入力された値をそのまま SQL 文につなげている",
      "why": "外部から SQL の命令を仕込まれ、データを盗まれたり消されたりする",
      "fix": "プレースホルダー（? や :name）を使い、値は別に渡す"
    }
  },
  "tool_map": {
    "gitleaks": { "*": "R-001" },
    "ruff": { "S105": "R-001", "S106": "R-001", "S608": "R-012" }
  },
  "kit_checks": [
    { "id": "K-001", "rule": "R-020", "pattern": "@(app|router)\\.(get|post|put|delete)\\(", "files": ["*.py"] }
  ]
}
```

### 5.2 項目

| 項目 | 意味 |
|---|---|
| `schema_version` | このデータの形の版。形を変えたら上げる |
| `kit_version` | キットの版 |
| `rules` | ルール ID ごとの、名称・重大度・通知文に使う3つの文。有効（`active`）なルールだけを入れる |
| `tool_map` | 検査ツールの番号から、自社のルール ID を引く表。検査結果の変換に使う |
| `kit_checks` | キット独自の簡易チェックの一覧 |

- 作成日時は入れない（1章の決まり）。
- 違反例・正常例や詳しい説明は入れない。フックが読む量を減らし、起動を速くするため。詳しい説明は Skill 側に生成する。

## 6. プロジェクトの設定（.claude/security-kit.json）

各プロジェクトでの、キットの動かし方を書く。初期化コマンドが作る。

### 6.1 例

```json
{
  "kit_version": "0.1.0",
  "mode": "warn",
  "level": 1,
  "exclude": ["tests/fixtures/**"],
  "exceptions": []
}
```

### 6.2 項目

| 項目 | 意味 | 値 |
|---|---|---|
| `kit_version` | このプロジェクトが前提にするキットの版。PR 時の導入確認で、古くないかを見る（FR-33） | |
| `mode` | 警告モードかどうか（FR-25） | `warn`（止めずに警告）/ `enforce`（止める） |
| `level` | 適用する段階 | `1` / `2` |
| `exclude` | 先輩役の検査から外すフォルダ | |
| `exceptions` | 期限つきの例外の一覧（4章） | |

- 警告モードの切り替えは、環境変数ではなくこのファイルで行う。フックと PR の判定の両方が同じ値を見るため、各自の PC と PR で判定がずれない。
- このファイルは `.claude/` の下にあるので、変更には承認者のレビューが必須になる（FR-38）。勝手に警告モードへ戻したり、検査から外すフォルダや例外を増やしたりできない。

## 7. セッションの状態

同じ指摘を繰り返さないことと、作業の区切りの検査のために、フックがセッションごとに持つ一時的な記憶である。

| 項目 | 意味 | 使う場面 |
|---|---|---|
| `session` | Claude Code のセッションの番号 | ファイルの名前に使う |
| `changed_files` | このターンで Claude が書いたファイル | 作業の区切りの検査の対象を決める |
| `notified` | すでに通知した指摘の指紋（8.3）の一覧 | 同じ指摘を2回通知しない |
| `pending_advice` | まだ伝えていない助言 | 作業のまとめに載せる |
| `stop_continued` | このターンで、すでに応答を続けさせたか | 続けさせるのを1ターンに1回に限る |
| `tool_missing_notified` | 「検査ツールが未導入」と知らせたか | セッションで1回だけ知らせる |

- 7日たったものは、フックが起動時に消す。

## 8. 記録

### 8.1 先輩役の記録（各自の PC）

指摘1件につき1行を書く。相談コマンドの利用も1行として書く。

```json
{"ts":"2026-11-13T14:21:57+09:00","kit":"0.1.0","project":"example-app","session":"3f9a1c","timing":"post","rule":"R-012","severity":"warn","tool":"ruff","tool_rule":"S608","file":"app/db.py","line":42,"fp":"a1b2c3d4e5f60718","action":"notified","outcome":"fixed","mode":"warn"}
```

| 項目 | 意味 | 値 |
|---|---|---|
| `ts` | 日時 | |
| `kit` | キットの版 | |
| `project` | リポジトリの名前 | |
| `session` | セッションの番号 | |
| `timing` | いつの検査か | `pre`（書く前）/ `post`（書いた直後）/ `stop`（作業の区切り）/ `consult`（相談） |
| `rule` | ルール ID。対応付けが無い指摘は空 | |
| `severity` | 重大度 | `block` / `warn` / `advise` |
| `tool`、`tool_rule` | 検査ツールと、そのツールでの番号 | |
| `file`、`line` | 場所（リポジトリからの相対パス） | |
| `fp` | 指摘の指紋（8.3） | |
| `action` | 先輩役がしたこと | `blocked`（止めた）/ `notified`（通知した）/ `summarized`（まとめに載せた）/ `skipped`（ツールが無く飛ばした） |
| `outcome` | 結果（FR-44） | `fixed`（直した）/ `open`（未対応）/ `excepted`（例外・除外）/ `unknown` |
| `mode` | そのときのモード | `warn` / `enforce` |

- **患者データのルール（R-005）の記録では、ファイルの名前を書かない。** フォルダと拡張子だけを書く。ファイルの名前に患者の氏名や番号が入っていることがあるためである。PR 時の結果（8.2）でも同じにする。
- `outcome` は、最初は `unknown` で書く。次の検査で同じ指紋の指摘が消えていれば `fixed`、残っていれば `open` として、結果の行を追記する（前の行は書き換えない）。

### 8.2 PR 時の結果（GitHub Actions の成果物）

これを正とする記録とする（FR-40）。

```json
{
  "schema_version": 1,
  "kit_version": "0.1.0",
  "repo": "monigairu/example-app",
  "pr": 12,
  "base": "（取り込み先のコミット）",
  "head": "（PR の先頭のコミット）",
  "mode": "enforce",
  "verdict": "fail",
  "tools": [
    { "name": "semgrep", "version": "（固定した版）", "status": "ok" }
  ],
  "findings": [
    { "rule": "R-012", "severity": "warn", "tool": "semgrep", "tool_rule": "（番号）", "file": "app/db.py", "line": 42, "fp": "a1b2c3d4e5f60718" }
  ],
  "existing": { "R-012": 3 },
  "new_suppressions": [
    { "file": "tests/test_auth.py", "line": 8, "tool": "gitleaks", "reason": "テスト用のダミーの鍵" }
  ],
  "exceptions_used": ["EX-2026-001"]
}
```

| 項目 | 意味 |
|---|---|
| `verdict` | 判定。`pass`（成功）/ `fail`（失敗） |
| `tools` | 動かした検査ツールと版、結果（`ok` / `error`）。検査が動かなかったことも記録に残す |
| `findings` | 今回の PR で増えた指摘（FR-39） |
| `existing` | 以前からある指摘の、ルールごとの件数。判定には使わない |
| `new_suppressions` | 今回の PR で増えた「問題ない」の印（基本設計書 3.11） |
| `exceptions_used` | 判定で使った例外 |

### 8.3 指摘の指紋

同じ指摘かどうかを見分けるための短い文字列である。重複した通知を防ぐことと、「直した／未対応」の判定に使う。

| 指摘の種類 | 指紋の作り方 |
|---|---|
| 秘密情報（R-001） | ルール ID、ファイルの場所、行番号から作る。該当の行の中身は使わない |
| それ以外 | ルール ID、ファイルの場所、該当の行の中身（空白を除く）から作る |

- 指紋は、上の材料をハッシュ（元に戻せない変換）にかけた値の先頭16文字とする。行の中身そのものは、どこにも保存しない。
- 行番号ではなく行の中身を使うのは、上に行が増えて番号がずれても、同じ指摘として扱うためである。
- 秘密情報だけは中身を使わない。秘密情報から作った値を残さないためである。

## 9. 集計

### 9.1 集計のデータ（metrics/）

週ごとに1ファイルを作る（例：`metrics/2026-W47.json`）。ルールごとの件数だけを持ち、個人やファイルの名前は持たない（NFR-12）。

```json
{
  "week": "2026-W47",
  "projects": 3,
  "rules": {
    "R-012": { "pr_new": 2, "pr_existing": 3, "suppressions_added": 0, "exceptions_active": 0 }
  },
  "false_positive_reports": { "R-001": 1 },
  "adoption": { "projects_with_kit": 3, "projects_total": 3 }
}
```

### 9.2 成功指標と、数字の出どころ

要件定義書13章の成功指標が、どのデータから出せるかを示す。

| 成功指標 | 数字の出どころ | 第一弾で自動で集められるか |
|---|---|---|
| PR 段階まで残った指摘件数 | PR 時の結果（`findings`） | 集められる |
| 再発率 | PR 時の結果と、ルールの `feedback_applied`（反映した日より後の件数） | 集められる |
| 「止める」ルールの誤検知率 | PR 時の「止める」の指摘のうち、印や報告コマンドの Issue で誤りとされた割合 | 集められる |
| 導入率 | PR 時の導入確認（FR-33） | 集められる |
| すり抜けテスト合格率 | キットの CI の結果 | 集められる |
| 修正採用率、警告の無視率 | 各自の PC の記録にしか無い | 第一弾では測らない。「PR 段階まで残った指摘件数」で代える |
| 相談コマンドの利用回数 | 各自の PC の記録にしか無い | 第一弾では測らない。パイロットの終わりのふりかえりで聞く |
| 重大事故件数 | 人が Issue に記録する | 手作業 |

**各自の PC の記録が必要な指標の扱い**

- 第一弾の数字は、PR 時の記録から自動で出せるものだけにする。メンバーに手作業で数字を出してもらう方法は、続かないため採らない。
- 各自の PC の記録は集めない。本人の画面に出す作業のまとめ（FR-19）と、「直した／未対応」の判定に使う。
- 手元で直されなかった警告は PR に残るので、「PR 段階まで残った指摘件数」が、無視された警告の件数の代わりになる。
- 各自の PC の記録を自動で集める方法（Claude Code 標準の記録出力。FR-45）は、商用契約へ移行するときに検討する。
