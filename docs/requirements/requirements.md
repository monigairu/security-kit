## 1. 背景

- 当社（（社名））では、Claude Code などの AI コーディングツールを使った開発が中心になりつつある。
- 一方で、AI 開発におけるセキュリティの社内規程・ガイドラインはまだ存在しない。
- 2026年は、AI 生成コードの脆弱性、悪性パッケージ（サプライチェーン攻撃）、AI エージェント経由の情報漏えいが急増しており、開発工程そのものが攻撃の入口になっている。
- メンバー全員がセキュリティに詳しいわけではなく、相談できる詳しい人が常に隣にいるわけでもない。
- 今後、歯科の診断画像・カルテを扱う案件が控えており、患者データを扱う前に開発時のセキュリティの土台を整える必要がある。

## 2. 目的

1. **その場で気づかせ、教える**：コーディング中に、セキュリティに強い先輩のように「そこ危ないよ」と一声かけ、理由と直し方を伝える。メンバーが指摘から学び、同じミスを繰り返さなくなることを目指す。
2. **ルールを統一する**：メンバーや使う AI ツールが違っても、同じルールで判定されるようにする（ガバナンスの統一）。
3. **重大な事故だけは確実に止める**：秘密情報の漏えいや悪性パッケージの導入など、被害の大きい操作はその場で止める。
4. **証跡を残す**：ルールの変更履歴と指摘の記録を残し、顧客や監査に説明できるようにする。

本キットのルール定義は、当社の **AI ガバナンス方針（AI 開発セキュリティガイドライン）の実体** を兼ねる。

## 3. 基本方針

| 方針 | 内容 |
|---|---|
| 先輩が主役、安全装置は土台 | 中心は「気づかせて教える」仕組み。止める仕組みは、先輩がいても起きる事故への保険として最小限に入れる |
| 黙って直さず、説明してから直す | AI が問題に気づいたら、理由と直し方を人に伝えてから修正する。人が学べることを重視する |
| 止めるのは最小限 | 「止める」は誤検知がほぼ無く、被害の大きいものだけ。それ以外は警告・助言とし、開発スピードを落とさない |
| 標準に乗り、差分だけ持つ | 公開の標準（Project CodeGuard、OWASP 等）を取り込み、自社で持つのは社内独自のルールと対応付けだけにする |
| 元データは1つ | ルールは YAML のみで管理する。文書・設定・一覧表はすべてそこから自動生成し、手で別々に書かない |
| 独立性の原則 | PR 時の最終判定には、コードを書いた AI と別ベンダーの AI、または AI ではない検査ツールを使う |
| 段階的に強くする | まず警告だけで運用して誤検知を測り、問題の少ないルールから順に強める |

## 4. 利用者・関係者

| 区分 | 役割 | 本キットとの関わり |
|---|---|---|
| 開発メンバー | AI ツールでコードを書く | 先輩役からの声かけを受ける、相談コマンドを使う |
| ルール管理者 | ルールの作成・更新（当面は作成者） | リポジトリを管理し、届いた更新提案を確認する |
| 承認者 | ルール変更・例外の承認 【要確認】 | PR をレビューし、例外を許可する |
| 非エンジニア利用者 | AI ツールで簡単な作業をする 【要確認：いるか】 | 最も厳しい設定で利用する |
| 将来：歯科案件チーム | 患者データを扱う開発 | 強化版ルール（Lv2）の対象 |

## 5. 全体像

### 5.1 部品と役割

| 部品 | 役割 | たとえ |
|---|---|---|
| ルール（YAML） | セキュリティの観点の元データ。ここから他の全部を生成 | 社内の規程集 |
| CLAUDE.md | 毎回必ず読む最重要ルール（数行） | 机に貼った注意書き |
| Skill | 観点の詳しい説明・直し方・伝え方 | 先輩の知識と話し方 |
| 声かけ Hook | コードを書いた直後に検査し、気になる点を AI に伝える | 先輩が横から画面をのぞくタイミング |
| 相談コマンド | 人から「これ大丈夫？」と聞く窓口 | 先輩の席 |
| 禁止設定・サンドボックス | 先輩がいても起きる事故への保険 | 会社の安全装置 |
| PR 時チェック | マージ前の最終確認（3層） | 社外の検査員 |
| 監査役（第二弾） | 要件・設計段階で脅威を洗い出す | 設計図の審査担当 |

### 5.2 先輩役の動きの例

1. Claude が、入力値をそのまま SQL 文につなげるコードを書く。
2. 書いた直後に声かけ Hook が検査ツールを実行し、「SQL インジェクションの可能性（ルール R-0xx）」と Claude に伝える。
3. Claude が Skill を参照し、利用者にこう伝える：「ひとこと：入力をそのまま SQL につなげると、外部から命令を仕込まれる危険があります。プレースホルダーという安全な書き方に直しますね」
4. 修正して作業を続ける。

## 6. 対象範囲

### 6.1 対象とする工程

| 工程 | 内容 | 担当する仕組み | 起動 | 段階 |
|---|---|---|---|---|
| 書いている最中 | 書いたコード・設定を検査し、一声かける。危険な操作は止める | 声かけ Hook、Skill、禁止設定、サンドボックス | 自動 | 第一弾 |
| 気になったとき | 人からの相談に答える | 相談コマンド | 手動 | 第一弾 |
| PR（変更依頼）時 | マージ前の最終チェック | 3層チェック（9.4 参照） | 自動 | 第一弾 |
| 要件・設計段階 | 要件定義書・設計書から脅威を洗い出す | 監査役 | 手動 | 第二弾（歯科案件の前） |

### 6.2 対象とするセキュリティ領域

| 扱い | 領域 |
|---|---|
| ◯ 対象 | アプリのコード、API、AI・LLM・MCP、依存ライブラリ、秘密情報、構成ファイル（Dockerfile、IaC、Claude Code の設定等）、要件・設計 |
| △ 一部対象（設定がファイル化されている場合） | 権限（IAM）、データベース・データ、クラウド設定、ネットワーク、CI/CD、ログ出力 |
| ✕ 対象外 | 下記「7. 対象外」を参照 |

### 6.3 対象とするツール・環境

- AI コーディングツール：Claude Code（主）
- 言語：Python（主）
- パッケージ管理：pip / uv / poetry
- ソース管理：GitHub（非公開リポジトリ）
- OS：【要確認】macOS / Linux / Windows（WSL2）のどれを対象にするか

## 7. 対象外（このキットでは扱わない）

- 運用中システムの監視・監査・インシデント対応
- 完成したシステム全体の網羅的な脆弱性診断（必要に応じて外部診断を利用する）
- フィッシング対策、社員教育全般
- 物理的なセキュリティ、端末の紛失対策
- Claude Code 以外の AI コーディングツールへの対応（第一弾では対象外。ルール定義は将来の拡張を妨げない形にする）

> 【要確認】会議では監査役の対象に「完成品・運用中のもの」も挙がっていた。本書では、完成品は PR 時の3層チェックが担い、運用中のものは対象外とする。この分担について承認者と合意する。

## 8. 前提・制約

- 当社にはまだ AI 開発に関する社内規程がない。そのため、公開されている標準を当社ルールの土台として採用する。
- 少人数チームであり、MDM（会社 PC の一括管理）は無い。
- Claude は各メンバーの個人契約である。管理画面から設定を一括配布する仕組みは使えないため、設定は各自の PC へセットアップスクリプトで配置し、PR 時のチェックを最後の砦とする。
- 開発（ステップ0〜3）は作成者の私用 PC で行う。
- 開発中のリポジトリ・PC には、患者データ・顧客データ・本番データを置かない。
- スタートアップの開発スピードを落とさないことを重視する。

## 9. 機能要件

優先度：**Must**（第一弾で必須）／**Should**（第一弾で望ましい）／**Could**（余裕があれば・将来）

### 9.1 ルール管理

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | ルールは YAML ファイルを唯一の元データとして管理する | Must |
| FR-02 | 各ルールは次の項目を持つ：ID、名称、重大度、領域、根拠（OWASP・CodeGuard 等の番号）、説明、安全な直し方、違反例、正常例、検出方法、検出の確実性、担当者（owner）、最終見直し日（last_reviewed） | Must |
| FR-03 | ルール本文は Project CodeGuard 等の公開標準を取り込み、当社独自のルールと根拠の対応付けのみを YAML で持つ | Must |
| FR-04 | 生成スクリプト（build.py）で、YAML から次を自動生成する：①AI ガバナンス方針書 ②CLAUDE.md ③Skill ④Claude Code 設定ファイル ⑤PR 時の AI レビュー用ガイドライン（AGENTS.md 等） ⑥閲覧用の一覧表（Excel / CSV） | Must |
| FR-05 | ルールの変更は GitHub の PR で受け付け、承認者のレビューを必須にする | Must |
| FR-06 | 一覧表は閲覧専用とし、編集は常に YAML 側で行う | Must |

### 9.2 先輩役（主役）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-10 | 声かけ Hook：AI がコード・設定ファイルを書いた直後に、変更箇所を検査ツール（Semgrep、Bandit、gitleaks、Trivy 等）で検査し、結果をルール ID 付きで AI に伝える | Must |
| FR-11 | Skill：ルールごとの詳しい説明、安全な直し方、伝え方を提供する | Must |
| FR-12 | 説明してから直す：AI は指摘を受けたら、黙って修正せず、理由と直し方を利用者に一言伝えてから修正する | Must |
| FR-13 | 伝え方の型：指摘は「何が危ないか／なぜ危ないか／どう直すか／詳しく知りたい場合の参照先」を、初心者にもわかる日本語で短く伝える | Must |
| FR-14 | 重大度で出し分ける：「止める／警告／助言」の3段階とし、助言レベルはまとめて伝えるなど、作業を邪魔しない頻度にする | Must |
| FR-15 | 認可の観点：API やデータアクセスを書くときは、「誰がアクセスできるか」を確認し、気になる点を利用者に一言伝える（検査ツールでは見つけにくい観点を補う） | Should |
| FR-16 | 相談コマンド：利用者が「これ大丈夫？」と聞くと、関係するルールに沿って回答する | Must |
| FR-17 | 報告コマンド：誤検知やルールの提案を、GitHub の Issue として登録できる | Should |

### 9.3 安全装置（土台）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-20 | 設定ファイルで次を禁止する：.env・鍵ファイル等の読み取り、確認なしで何でも実行するモード（bypass）、sudo | Must |
| FR-21 | サンドボックスを有効にし、作業ディレクトリ外のファイル操作と、許可していない通信先へのアクセスを制限する | Must |
| FR-22 | パッケージ導入前チェック：pip / uv / poetry でのインストールと、requirements.txt・pyproject.toml の編集を検知し、①PyPI に実在するか ②初回公開日が新しすぎないか ③OSV に既知の脆弱性・悪性パッケージ情報がないか、を確認する | Must |
| FR-23 | 公開直後のバージョンを入れない設定（cooldown、例：7日）をプロジェクトのひな形に含める | Must |
| FR-24 | ブロック時は、ルール ID・理由・安全な代替手段・例外申請の方法を必ず表示する | Must |
| FR-25 | 全ルールを「警告のみ」で動かすモードを持つ（パイロット運用用） | Must |
| FR-26 | CLAUDE.md・SKILL.md・.claude/・.mcp.json などのルール・設定ファイルに、不審な記述（見えない文字、外部送信、権限を緩める記述）がないか検査する | Should |

### 9.4 PR 時の最終チェック（3層）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-30 | 層1（AI ではない検査ツール）：Semgrep（OWASP 対応ルール）、Bandit、gitleaks、pip-audit、Trivy を GitHub Actions で自動実行する | Must |
| FR-31 | 層2（別ベンダーの AI レビュー）：コードを書いた AI と別ベンダーの AI（第一候補：OpenAI Codex のコードレビュー）が、build.py の生成したガイドラインに沿ってレビューする | Should |
| FR-32 | 層3（自己チェック）：Claude Code の /security-review を、書き終わった後の自己確認として使えるようにする。最終判定には使わない | Should |
| FR-33 | キット導入確認：PR 時に、そのプロジェクトにキットの設定が入っているか、バージョンが古くないかを確認する | Should |
| FR-34 | 各プロジェクトのワークフローは、キット側の共通ワークフローを呼び出すだけの形にする（ルール変更時に全プロジェクトを書き換えない） | Should |

### 9.5 記録・例外

| ID | 要件 | 優先度 |
|---|---|---|
| FR-40 | 指摘・ブロックの発生を、ルール ID・日時・対象・結果（修正した／無視した）とともに記録する | Must |
| FR-41 | 例外は「誰が・なぜ・いつまで」を YAML に記録し、期限切れで自動的に無効にする | Should |
| FR-42 | 記録を集計し、ルール別の発生件数・誤検知率・無視率・再発率を確認できるようにする | Should |

### 9.6 ルールの保守

| ID | 要件 | 優先度 |
|---|---|---|
| FR-50 | 悪性パッケージ・脆弱性情報は、外部データベース（OSV 等）を毎回参照し、自前で更新しない | Must |
| FR-51 | 取り込んでいる標準（CodeGuard、Semgrep ルール等）はバージョンを固定し、新版が出たら更新の PR が自動で作られるようにする（Dependabot 等） | Should |
| FR-52 | 週1回、AI が最新のセキュリティ動向（IPA「AI セキュリティ短信」、OWASP 等）を読み、ルール案を PR の下書きとして提案する。採用は人が判断する | Could |
| FR-53 | 最終見直し日から一定期間（例：6か月）が過ぎたルールを、CI で警告する | Should |
| FR-54 | ルールを変更するとテストが自動実行され、バージョン番号付きでリリースし、変更内容の一覧（changelog）を自動生成する | Should |
| FR-55 | 重大な事件・脆弱性が出たときは、当日中にルールを追加して緊急リリースできる手順を用意する | Should |

### 9.7 監査役（第二弾）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-60 | 要件定義書・設計書を読み、STRIDE と OWASP Agentic Top 10 で脅威を洗い出す | Could |
| FR-61 | 出力は「脅威・発生シナリオ・影響・根拠となる記述箇所・確認すべき質問」の表形式とする | Could |
| FR-62 | 作り手の会話履歴を引き継がず、読み取り専用で動作する | Could |
| FR-63 | 使う AI モデルを差し替えられる設計にし、作り手と別ベンダーのモデルで動かせるようにする | Could |

### 9.8 配布

| ID | 要件 | 優先度 |
|---|---|---|
| FR-70 | Skill・Hook・相談コマンド・監査役を、Claude Code のプラグインとして配布する | Must |
| FR-71 | リポジトリを社内プラグインの配布元（マーケットプレイス）の形にする | Should |
| FR-72 | 強制設定は、各自の PC に配置するセットアップスクリプトで配る。将来 Team プラン等に移行した場合は管理画面配布に切り替えられる形にする | Must |
| FR-73 | 初期化コマンドで、新しいプロジェクトに設定ファイル・cooldown 設定・PR チェック用ワークフローを自動生成する | Should |

## 10. 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| NFR-01 | 応答性能 | 声かけ Hook・導入前チェックは通常 2 秒以内に返す（目安）。開発の邪魔にならないことを優先する |
| NFR-02 | 障害時の動作 | 外部 API（PyPI・OSV）が使えないとき、悪性照合は「止める」、公開日確認は「警告」とする（重大度ごとに定義） |
| NFR-03 | 再現性 | 「止める」判定は正規表現・API 照合・検査ツールなど決定的な方法のみで行い、AI の判断には任せない |
| NFR-04 | 説明の質 | 指摘は日本語で、セキュリティの前提知識がない人にも理解できる表現にする |
| NFR-05 | 独立性 | PR 時の最終判定は、コードを書いた AI と別ベンダーの AI、または AI ではない検査ツールで行う |
| NFR-06 | テスト | 各ルールに違反例・正常例のテストを持ち、ルール変更時に CI で自動実行する |
| NFR-07 | 耐性 | よくあるすり抜け手口（Python 経由での読み取り、長いコマンド連結、シンボリックリンク等）のテストを用意し、合格を確認する |
| NFR-08 | 自己防衛 | キット自体のルールファイル・設定の変更は PR 経由のみとする |
| NFR-09 | 保守性 | ルール 1 件の追加が、YAML の追記とテストの追加だけで完了する。ルール管理者の定常作業は週15分程度を目安とする |
| NFR-10 | 透明性 | 全ルールとその根拠を、方針書として社内の誰でも読める形で公開する |
| NFR-11 | 更新 | Claude Code は最新版の利用を前提とし、最低バージョンを方針書に明記する |

## 11. 第一弾で「止める」ルール（案）

| ID | ルール | 理由 |
|---|---|---|
| R-001 | 秘密情報（API キー・パスワード等）をコードに直接書かない | 漏えい時の被害が大きく、検出の誤りが少ない |
| R-002 | .env・鍵ファイル・認証情報ファイルを AI に読ませない | AI 経由での漏えい・外部送信を防ぐ |
| R-003 | 確認なしで何でも実行するモード（bypass）を使わない | 他の全ての守りが無効になるため |
| R-004 | 実在しない・悪性と判明しているパッケージを入れない | サプライチェーン攻撃・スロップスクワッティング対策 |
| R-005 | 患者データ・本番データを AI や外部サービスに渡さない | 法令上・信頼上の影響が最も大きい |

上記以外のルールは「警告」または「助言」から開始し、記録を見て昇格を判断する。

|---|---|---|
| 使ってよい AI サービス | Claude（Claude Code 含む）を標準とし、PR レビュー用に OpenAI Codex を追加。それ以外は申請制 | 代表・CTO |
| データの区分 | 公開／社内／機密／患者データ の4区分。患者データは AI・外部サービスへの入力禁止 | 代表・CTO |
| 例外の承認者 | CTO（不在時は代表） | 代表 |
| 見直しの頻度 | 週1回の更新提案の確認、四半期に1回の全体見直し | ルール管理者 |

## 15. リスクと対策

| リスク | 対策 |
|---|---|
| 指摘が多すぎて無視される | 重大度で出し分け、助言はまとめて伝える。警告モードで先に測る |
| 検査ツールでは認可の漏れ・ロジックの穴が見つからない | Skill で認可の観点を確認させ（FR-15）、PR 時の別ベンダー AI レビューと監査役で補う |
| 個人契約のため、設定をメンバー自身が外せる | ルールへの合意を前提に運用し、PR 時のキット導入確認（FR-33）と3層チェックで補う。人数が増えたら管理画面からの強制配布に移行する |
| Hooks がすり抜けられる | 強制は設定・サンドボックスで行い、Hooks は声かけと記録の役割にする。すり抜けテストを継続実行する |
| 別ベンダーの AI にコードを送ることになる | 患者データ・秘密情報をコードに含めない運用を徹底する。送信先のデータの扱い（学習利用の有無等）を契約前に確認する 【要確認】 |
| ルールの保守が負担になる | 外部データベース・標準に任せ、自社分だけを持つ。更新は半自動化する |
| Claude Code の仕様変更で動かなくなる | 最低バージョンを定め、更新時にテストを再実行する |
| 外部 API（PyPI・OSV）の障害 | 重大度ごとに障害時の動作を定義する（NFR-02） |

## 17. 用語集

| 用語 | 説明 |
|---|---|
| Claude Code | ターミナルで動く AI コーディングツール |
| Hook | Claude Code が操作をする直前・直後に、必ず実行されるチェック用スクリプト |
| Skill | 必要なときに AI が読み込む、専門知識や手順・振る舞いのまとまり |
| プラグイン | Skill・Hook・コマンドなどを1つにまとめて配布できる、Claude Code の仕組み |
| サンドボックス | AI が実行するコマンドの、触れるファイルや通信先を OS レベルで囲い込む仕組み |
| CLAUDE.md | Claude Code が毎回読み込む、プロジェクトの基本ルールファイル |
| AGENTS.md | AI レビューツール（Codex 等）が読み込む、レビュー基準などを書いたファイル |
| PR（プルリクエスト） | 変更をレビューしてから取り込むための依頼 |
| Issue | GitHub 上の課題票。不具合の報告や提案を登録する |
| CI / GitHub Actions | コードの変更時に、テストやチェックを自動実行する仕組み |
| Dependabot | 使っている部品の新版が出たときに、更新の PR を自動で作る GitHub の機能 |
| Semgrep | コードの危ない書き方を、ルールに沿って機械的に検出するツール |
| Bandit | Python 専用のセキュリティ検査ツール |
| gitleaks | API キーなどの秘密情報の混入を検出するツール |
| pip-audit | 使っているライブラリに既知の脆弱性がないか調べるツール |
| Trivy | 構成ファイル（Dockerfile、IaC 等）の危ない設定などを検出するツール |
| IaC | クラウドなどのインフラ設定を、コードとして書いて管理する方法 |
| 認可 | 「誰に何を許すか」を決める仕組み。漏れがあると、他人のデータが見えるなどの問題が起きる |
| サプライチェーン攻撃 | 使っているライブラリなどに悪意あるコードを仕込む攻撃 |
| スロップスクワッティング | AI がでっち上げたパッケージ名を、攻撃者が先回りして登録しておく攻撃 |
| cooldown | 公開されて間もない新バージョンを、一定期間入れないようにする設定 |
| OSV | オープンソースの脆弱性・悪性パッケージ情報のデータベース |
| STRIDE | 脅威を6分類（なりすまし・改ざん・否認・情報漏えい・サービス妨害・権限昇格）で洗い出す手法 |
| 要配慮個人情報 | 病歴・診療情報など、法律上とくに慎重な扱いが求められる個人情報 |
