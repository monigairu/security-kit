## 1. 背景

- 当社（（社名））では、Claude Code などの AI コーディングツールを使った開発が中心になりつつある。
- 一方で、AI 開発におけるセキュリティの社内規程・ガイドラインはまだ存在しない。
- 2026年は、AI 生成コードの脆弱性、悪性パッケージ（サプライチェーン攻撃）、AI エージェント経由の情報漏えいが急増しており、開発工程そのものが攻撃の入口になっている。
- 2026年3月には、検査ツール（Trivy）の公式 Action が乗っ取られ、CI の秘密情報が盗まれた。検査する仕組み自体も攻撃の対象になっている。
- メンバー全員がセキュリティに詳しいわけではなく、相談できる詳しい人が常に隣にいるわけでもない。
- 今後、歯科の診断画像・カルテを扱う案件が控えており、患者データを扱う前に開発時のセキュリティの土台を整える必要がある。

## 2. 目的

1. **その場で気づかせ、教える**：コーディング中に、セキュリティに強い先輩のように「そこ危ないよ」と一声かけ、理由と直し方を伝える。メンバーが指摘から学ぶことと、繰り返し出る指摘をルールへ戻して AI が同じ書き方をしなくなることの両方を目指す。
2. **ルールを統一する**：メンバーや使う AI ツールが違っても、同じルールで判定されるようにする（ガバナンスの統一）。
3. **重大な事故だけは確実に止める**：秘密情報の漏えいや悪性パッケージの導入など、被害の大きい操作はその場で止める。
4. **証跡を残す**：ルールの変更履歴と指摘の記録を残し、顧客や監査に説明できるようにする。

本キットのルール定義は、当社の **AI ガバナンス方針（AI 開発セキュリティガイドライン）の実体** を兼ねる。

## 3. 基本方針

| 方針 | 内容 |
|---|---|
| 先輩が主役、安全装置は土台 | 中心は「気づかせて教える」仕組み。止める仕組みは、先輩がいても起きる事故への保険として最小限に入れる |
| 黙って直さず、説明してから直す | AI が問題に気づいたら、理由と直し方を人に伝えてから修正する。人が学べることを重視する |
| 止めるのは最小限 | 「止める」は誤検知がほぼ無く、被害の大きいものだけ。それ以外は警告・助言とし、開発スピードを落とさない |
| 技術で止めきれないものは運用で守る | 機械的に検出できない事項（患者データ等）は、環境の制限と運用ルールで守り、その旨をルールに明記する |
| 標準に乗り、差分だけ持つ | 公開の標準（Project CodeGuard、OWASP 等）を取り込み、自社で持つのは社内独自のルールと対応付けだけにする |
| 元データは1つ | 自社のルールは YAML のみで管理する。文書・設定・一覧表はそこから自動生成し、手で別々に書かない |
| 独立性の原則 | PR 時の最終判定には、コードを書いた AI と別ベンダーの AI、または AI ではない検査ツールを使う |
| AI を通らない経路も守る | 人が直接コミットした変更や、別のツールで書いた変更にも同じ検査をかける |
| 検査する仕組み自体も守る | CI とキット自体が攻撃されても被害が広がらないようにする（バージョンの固定、最小権限） |
| 段階的に強くする | まず警告だけで運用して誤検知を測り、問題の少ないルールから順に強める |

## 5. 全体像

### 5.1 部品と役割

| 部品 | 役割 | たとえ |
|---|---|---|
| ルール（YAML） | 自社のセキュリティの観点の元データ。ここから方針書や設定を生成 | 社内の規程集 |
| CLAUDE.md | 毎回必ず読む最重要ルール（数行） | 机に貼った注意書き |
| Skill | 観点の詳しい説明・直し方・伝え方 | 先輩の知識と話し方 |
| 声かけ Hook | コードを書いた直後と作業の区切りに検査し、気になる点を AI に伝える | 先輩が横から画面をのぞくタイミング |
| 相談コマンド | 人から「これ大丈夫？」と聞く窓口 | 先輩の席 |
| 強制設定・サンドボックス | 先輩がいても起きる事故への保険 | 会社の安全装置 |
| 許可リスト | 使ってよい MCP サーバー・プラグインを限定する | 入館を許可した業者の名簿 |
| コミット前チェック | AI を通らない変更も含め、コミット前に秘密情報を検査する | 部屋を出る前の持ち物確認 |
| PR 時チェック | マージ前の最終確認（3層） | 社外の検査員 |
| 監査役（第二弾） | 要件・設計段階で脅威を洗い出す | 設計図の審査担当 |

### 5.2 先輩役の動きの例

1. Claude が、入力値をそのまま SQL 文につなげるコードを書く。
2. 書いた直後に声かけ Hook が検査ツールを実行し、「SQL インジェクションの可能性（ルール R-0xx）」と Claude に伝える。
3. Claude が Skill を参照し、利用者にこう伝える：「ひとこと：入力をそのまま SQL につなげると、外部から命令を仕込まれる危険があります。プレースホルダーという安全な書き方に直しますね」
4. 修正して作業を続ける。
5. 作業の終わりに、出た指摘と行った修正の一覧を利用者に示す。
6. 同じ指摘が繰り返し出るようなら、ルール管理者が CLAUDE.md やルールに反映し、AI が最初から安全な書き方をするようにする。

## 6. 対象範囲

### 6.1 対象とする工程

| 工程 | 内容 | 担当する仕組み | 起動 | 段階 |
|---|---|---|---|---|
| 書いている最中 | 書いたコード・設定を検査し、一声かける。危険な操作は止める | 声かけ Hook、Skill、強制設定、サンドボックス、許可リスト | 自動 | 第一弾 |
| 気になったとき | 人からの相談に答える | 相談コマンド | 手動 | 第一弾 |
| コミット前 | 秘密情報が混ざっていないか検査する（AI を通らない変更も対象） | コミット前チェック | 自動 | 第一弾 |
| PR（変更依頼）時 | マージ前の最終チェック | 3層チェック（9.4 参照） | 自動 | 第一弾 |
| 要件・設計段階 | 要件定義書・設計書から脅威を洗い出す | 監査役 | 手動 | 第二弾（歯科案件の前） |

### 6.2 対象とするセキュリティ領域

| 扱い | 領域 |
|---|---|
| ◯ 対象 | アプリのコード、API、AI・LLM・MCP、依存ライブラリ、秘密情報、構成ファイル（Dockerfile、IaC、Claude Code の設定等）、GitHub Actions のワークフロー、要件・設計 |
| △ 一部対象（設定がファイル化されている場合） | 権限（IAM）、データベース・データ、クラウド設定、ネットワーク、ログ出力 |
| ✕ 対象外 | 下記「7. 対象外」を参照 |

### 6.3 対象とするツール・環境

- AI コーディングツール：Claude Code（主）
- 言語：Python（主）
- パッケージ管理：uv（推奨）/ pip / poetry 【要確認：uv を標準にするか】
- ソース管理：GitHub（非公開リポジトリ、有料プラン。8章参照）
- OS：macOS / Linux / Windows は WSL2 のみ（案）。サンドボックスが Windows 単体では使えないため 【要確認】
- 権限モード：bypass は禁止。auto モードの扱いは FR-29 を参照

## 7. 対象外（このキットでは扱わない）

- 運用中システムの監視・監査・インシデント対応
- 完成したシステム全体の網羅的な脆弱性診断（必要に応じて外部診断を利用する）
- フィッシング対策、社員教育全般
- 物理的なセキュリティ、端末の紛失対策
- Claude Code 以外の AI コーディングツールへの対応（第一弾では対象外。ルール定義は将来の拡張を妨げない形にする。コミット前チェックと PR 時チェックはツールに関係なく働く）

> 【要確認】会議では監査役の対象に「完成品・運用中のもの」も挙がっていた。本書では、完成品は PR 時の3層チェックが担い、運用中のものは対象外とする。この分担について承認者と合意する。

## 8. 前提・制約

### 8.1 体制と環境

- 当社にはまだ AI 開発に関する社内規程がない。そのため、公開されている標準を当社ルールの土台として採用する。
- 少人数チームであり、MDM（会社 PC の一括管理）は無い。
- 開発（ステップ0〜3）は作成者の私用 PC で行う。
- 開発中のリポジトリ・PC には、患者データ・顧客データ・本番データを置かない。
- スタートアップの開発スピードを落とさないことを重視する。

### 8.2 契約と設定（キットより先に整える）

- **Claude は各メンバーの個人契約である。** 個人向けプランは、設定をオフにしない限り、Claude Code の内容もモデルの学習に使われる（保持は最長5年）。第一弾では、学習利用の設定をオフにすることを全員の必須事項とする。
- **歯科案件の前に、商用契約（Team プラン等）へ移行する。** 商用契約は既定で学習に使われず、管理画面から設定を配布できる 【要確認：最低席数・費用】。
- **PR レビュー用の別ベンダー AI（OpenAI Codex 等）も同じ扱いとする。** 個人向けプランは学習利用をオフにし、可能なら法人向けプランを使う。
- **GitHub は有料プラン（Pro または Team）を前提とする。** 無料プランの非公開リポジトリでは、レビュー必須（ブランチ保護）を強制できない。「PR 時のチェックが最後の砦」という設計は、この強制が前提になる。
- **設定の配布は2か所に行う。** 管理画面からの一括配布は個人契約では使えないため、各自の PC の強制設定ファイルと、各リポジトリ内の設定ファイルに置く（FR-72、FR-74）。PR 時のチェックを最後の砦とする。

## 9. 機能要件

優先度：**Must**（第一弾で必須）／**Should**（第一弾で望ましい）／**Could**（余裕があれば・将来）／**Lv2 必須**（歯科案件の着手前に必須）

### 9.1 ルール管理

| ID | 要件 | 優先度 |
|---|---|---|
| FR-01 | 自社のルールは YAML ファイルを唯一の元データとして管理する | Must |
| FR-02 | 自社独自のルールは次の項目を持つ：ID、名称、重大度、領域、根拠（OWASP・CodeGuard 等の番号）、説明、安全な直し方、違反例、正常例、検出方法、検出の確実性、担当者（owner）、最終見直し日（last_reviewed）。公開標準から取り込むルールは、対応付けに必要な項目（ID、根拠、重大度、検出方法、担当者、最終見直し日）だけを持つ | Must |
| FR-03 | 公開標準のルール本文は自社で書き写さない。Project CodeGuard は公式の Claude Code プラグインをそのまま導入し、当社独自のルールと根拠の対応付けのみを YAML で持つ 【要確認：CodeGuard の Skill 名が /security-review と衝突するという報告があり、実機で確認する】 | Must |
| FR-04 | 生成スクリプト（build.py）で、YAML から次を自動生成する：①AI ガバナンス方針書 ②CLAUDE.md ③Claude Code 設定ファイル | Must |
| FR-05 | ルールの変更は GitHub の PR で受け付け、承認者のレビューを必須にする。必須化は GitHub のブランチ保護で強制する | Must |
| FR-06 | 一覧表は閲覧専用とし、編集は常に YAML 側で行う | Must |
| FR-08 | build.py の生成対象に次を追加する：④独自ルール分の Skill ⑤PR 時の AI レビュー用ガイドライン（AGENTS.md 等） ⑥閲覧用の一覧表（Excel / CSV） | Should |

### 9.2 先輩役（主役）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-10 | 声かけ Hook（書いた直後）：AI がコード・設定ファイルを書いた直後に、変更したファイルだけを軽い検査（Ruff のセキュリティルール、gitleaks、少数の Semgrep ルール）で検査し、結果をルール ID 付きで AI に伝える | Must |
| FR-18 | 声かけ Hook（作業の区切り）：AI の応答が終わる時点で、変更全体を重い検査（Semgrep の全ルール、Bandit、Trivy 等）で検査し、結果をルール ID 付きで AI に伝える | Must |
| FR-11 | Skill：ルールごとの詳しい説明、安全な直し方、伝え方を提供する | Must |
| FR-12 | 説明してから直す：AI は指摘を受けたら、黙って修正せず、理由と直し方を利用者に一言伝えてから修正する | Must |
| FR-19 | 作業のまとめ：作業の終わりに、出た指摘と行った修正を一覧で利用者に示す。auto モードなどで画面を見ていなくても、後から読めるようにする | Should |
| FR-13 | 伝え方の型：指摘は「何が危ないか／なぜ危ないか／どう直すか／詳しく知りたい場合の参照先」を、初心者にもわかる日本語で短く伝える | Must |
| FR-14 | 重大度で出し分ける：「止める／警告／助言」の3段階とし、助言レベルはまとめて伝えるなど、作業を邪魔しない頻度にする | Must |
| FR-15 | 認可の観点：API やデータアクセスを書くときは、「誰がアクセスできるか」を確認し、気になる点を利用者に一言伝える（検査ツールでは見つけにくい観点を補う）。Lv2 では必須にする（FR-82） | Should |
| FR-16 | 相談コマンド：利用者が「これ大丈夫？」と聞くと、関係するルールに沿って回答する | Must |
| FR-17 | 報告コマンド：誤検知やルールの提案を、GitHub の Issue として登録できる | Should |

### 9.3 安全装置（土台）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-20 | 設定ファイルで次を禁止する：.env・鍵ファイル・認証情報ファイルの読み取り、sudo。読み取り禁止ルールが効くのは AI のファイル操作と cat などの認識できるコマンドまでなので、それ以外の経路は FR-21 で塞ぐ | Must |
| FR-21 | サンドボックスを有効にし、次を制限する：①作業ディレクトリ外への書き込み ②秘密情報ファイルの読み取り（サブプロセス経由を含む。denyRead 設定） ③秘密情報を含む環境変数の引き継ぎ（credentials 設定） ④許可リストにない通信先へのアクセス | Must |
| FR-22 | パッケージ導入前チェック：次の操作を検知して確認する。対象は、pip / uv / poetry でのインストール、requirements.txt・pyproject.toml の編集、その場で取得して実行するコマンド（uvx、pipx、npx 等。MCP サーバーの起動を含む）。確認内容は、①OSV に悪性パッケージ・既知の脆弱性の情報がないか ②初回公開日が新しすぎないか ③PyPI に実在するか（補助的な確認。攻撃者が先に名前を登録する手口には効かない）。uv の標準機能（uv audit、悪性パッケージ照合）で代替できる部分は自作しない 【要確認：悪性パッケージ照合はプレビュー版】 | Must |
| FR-23 | プロジェクトのひな形に次を含める：①公開直後のバージョンを入れない設定（cooldown、例：7日） ②ロックファイルの利用（間接的な依存まで固定し、PR 時に検査できるようにする） | Must |
| FR-24 | ブロック時は、ルール ID・理由・安全な代替手段・例外申請の方法を必ず表示する | Must |
| FR-25 | 全ルールを「警告のみ」で動かすモードを持つ（パイロット運用用） | Must |
| FR-26 | CLAUDE.md・SKILL.md・.claude/・.mcp.json などのルール・設定ファイルに、不審な記述（見えない文字、外部送信、権限を緩める記述）がないか検査する | Should |
| FR-27 | 許可リスト：MCP サーバー・プラグイン・Skill は、許可リストにあるものだけを使えるようにする（allowedMcpServers、strictKnownMarketplaces 設定）。リポジトリに含まれる MCP サーバーを自動で承認しない | Must |
| FR-28 | コミット前チェック：コミットの直前に gitleaks で秘密情報を検査する。AI を通らない変更も対象にし、GitHub に上がる前に止める。利用者が意図的に飛ばすこともできるため、PR 時の検査（FR-30）と併用する | Must |
| FR-29 | 権限モード：確認なしで何でも実行するモード（bypass）を設定で無効にする（disableBypassPermissionsMode）。auto モード（AI の操作を別の判定モデルが審査するモード。現在の既定）は、サンドボックスの有効化を条件に第一弾では認める 【要確認】。なお、bypass を無効にしても、bypass を指定した起動はエラーにならず、通知なしで通常のモードで動く（2026-11-13 の実機確認）。利用者が bypass で動いていると誤解しないよう、方針書とセットアップ時の案内で周知する | Must |

### 9.4 PR 時の最終チェック（3層）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-30 | 層1（AI ではない検査ツール）：次を GitHub Actions で自動実行する。コード：Semgrep（OWASP 対応ルール）、Bandit。秘密情報：gitleaks。依存ライブラリ：pip-audit、osv-scanner（ロックファイル全体を、悪性パッケージ情報も含めて照合）。構成ファイル：Trivy。ワークフロー：zizmor 等 | Must |
| FR-31 | 層2（別ベンダーの AI レビュー）：コードを書いた AI と別ベンダーの AI（第一候補：OpenAI Codex のコードレビュー）が、build.py の生成したガイドラインに沿ってレビューする。Lv2 では必須にする（FR-82） | Should |
| FR-32 | 層3（自己チェック）：Claude Code の /security-review を、書き終わった後の自己確認として使えるようにする。最終判定には使わない | Should |
| FR-33 | キット導入確認：PR 時に、リポジトリ内のキット設定（.claude/settings.json 等）が入っているか、バージョンが古くないかを確認する。各自の PC の設定は PR 時に確認できないため、強制設定（FR-72）とルールへの合意で補う | Should |
| FR-34 | 各プロジェクトのワークフローは、キット側の共通ワークフローを呼び出すだけの形にする（ルール変更時に全プロジェクトを書き換えない）。共通ワークフローが乗っ取られると全プロジェクトに影響するため、呼び出しはコミット SHA で固定する | Should |
| FR-35 | CI 自体の防御：①Action と検査ツールは、タグではなくコミット SHA・バージョンで固定する ②ワークフローの権限（permissions）は最小にする ③検査ジョブには秘密情報を渡さない | Must |
| FR-36 | AI レビュー（層2・層3）を CI で動かす場合は、社内メンバーの PR だけを対象にし、権限と渡す秘密情報を最小にする。PR のタイトル・本文・コメントに書かれた指示には従わせない | Must（FR-31・FR-32 を CI で使う場合） |

## 11. 第一弾で「止める」ルール（案）

| ID | ルール | 理由 | 止め方（決定的な方法） |
|---|---|---|---|
| R-001 | 秘密情報（API キー・パスワード等）をコードに直接書かない | 漏えい時の被害が大きく、検出の誤りが少ない | gitleaks を3か所で実行する（書いた直後、コミット前、PR 時） |
| R-002 | .env・鍵ファイル・認証情報ファイルを AI に読ませない | AI 経由での漏えい・外部送信を防ぐ | 読み取り禁止ルール（FR-20）と、サンドボックスの読み取り制限・環境変数の除去（FR-21） |
| R-003 | 確認なしで何でも実行するモード（bypass）を使わない | 他の全ての守りが無効になるため | 強制設定で無効にする（FR-29、FR-72） |
| R-004 | 悪性と判明している、または公開直後のパッケージを入れない | サプライチェーン攻撃・スロップスクワッティング対策 | 導入前チェック（FR-22）、cooldown とロックファイル（FR-23）、PR 時のロックファイル検査（FR-30） |
| R-005 | 患者データ・本番データを AI や外部サービスに渡さない | 法令上・信頼上の影響が最も大きい | 内容を機械的に見分けることはできないため、次の組み合わせで守る。技術：画像・カルテ系の拡張子とデータ置き場の読み取り禁止、通信先の許可リスト（FR-21）。運用：開発機・リポジトリに置かない（8章）、データ区分のルール（12章） |
| R-006 | 許可リストにない MCP サーバー・プラグインを入れない 【要確認】 | 悪性の Skill や MCP サーバーによる認証情報の窃取が報告されているため | 許可リスト（FR-27） |

## 13. 成功指標

数値はパイロット運用（ステップ4）の結果を見て確定する。集計はチーム単位で行う（NFR-12）。

コードを書くのは主に AI なので、「同じ人に同じ指摘が出るか」では人の学びを測れない。v0.4 では、再発率をルール単位の指標に変え、人の学びは別の指標で見る。

| 指標 | 意味 | 目標（仮） |
|---|---|---|
| PR 段階まで残った指摘件数 | 書いている最中に直せず、PR 時の検査で初めて見つかった件数（手前の仕組みが効いているか） | 継続的に低下 |
| 再発率 | CLAUDE.md・ルールへ反映した後も、同じルールの指摘が出続ける割合（AI への反映が効いているか） | 継続的に低下 |
| 修正採用率 | 指摘後に実際に直した割合 | 継続的に上昇 |
| 警告の無視率 | 警告を見ても直さなかった割合 | 継続的に低下 |
| 相談コマンドの利用回数 | メンバーが自分から確認しているか（人の学びの目安） | 継続的に利用がある |
| 理解度の確認 | 四半期に1回、よく出た指摘について短い確認を行う（人の学びの目安）【要確認：実施するか】 | 継続的に上昇 |
| 「止める」ルールの誤検知率 | 間違って止めた割合 | 5% 未満 |
| すり抜けテスト合格率 | 既知の回避手口を止められた割合 | 100% |
| 導入率 | キットを導入しているメンバー・プロジェクトの割合 | パイロット後 100% |
| 重大事故件数 | 秘密情報漏えい・悪性パッケージ導入 | 0 件 |

| 6. 継続改善 | 週次・四半期 | 更新提案の確認、ルール見直し記録 |

## 15. リスクと対策

| リスク | 対策 |
|---|---|
| 指摘が多すぎて無視される | 重大度で出し分け、助言はまとめて伝える。警告モードで先に測る |
| 検査が遅くて開発の邪魔になる | 書いた直後は軽い検査だけにし、重い検査は作業の区切りと PR 時に回す。ステップ2で実測する（NFR-01） |
| 人が画面を見ておらず、説明が読まれない（auto モード等） | 作業の終わりに指摘と修正のまとめを示す（FR-19）。繰り返す指摘はルールへ戻す（FR-56） |
| 検査ツールでは認可の漏れ・ロジックの穴が見つからない | Skill で認可の観点を確認させ（FR-15）、PR 時の別ベンダー AI レビューと監査役で補う。Lv2 では必須にする（FR-82） |
| 個人契約のため、入力したコードが学習に使われる | 学習利用の設定オフを必須にする。歯科案件の前に商用契約へ移行する（8章） |
| 個人契約のため、設定をメンバー自身が外せる | 上書きできない強制設定ファイルに置く（FR-72）。それでも本人は外せるため、ルールへの合意を前提に運用し、PR 時のキット導入確認（FR-33）と3層チェックで補う。商用契約への移行後は管理画面から配布する |
| Hooks がすり抜けられる | 強制は設定・サンドボックスで行い、Hooks は声かけと記録の役割にする。すり抜けテストを継続実行する |
| 検査ツールや CI が攻撃される（2026年3月の Trivy の事例） | Action と検査ツールをコミット SHA・バージョンで固定し、権限を最小にし、検査ジョブに秘密情報を渡さない（FR-35）。更新には cooldown をかける（FR-51） |
| キット自体が乗っ取られ、全員の PC に影響する | 管理者の2要素認証、ブランチ保護、プラグインのバージョン固定（FR-75、NFR-08） |
| 悪性の MCP サーバー・プラグイン・Skill を入れてしまう | 許可リスト方式にする（FR-27）。設定ファイルの不審な記述を検査する（FR-26） |
| AI レビューが PR 内の文章で操られる（プロンプトインジェクション） | 社内メンバーの PR だけを対象にし、権限と秘密情報を最小にする（FR-36）。最終判定は AI ではない検査ツールでも行う（NFR-05） |
| 別ベンダーの AI にコードを送ることになる | 患者データ・秘密情報をコードに含めない運用を徹底する。送信先のデータの扱い（学習利用の有無等）を契約前に確認する 【要確認】 |
| ルールの保守が負担になる | 外部データベース・標準に任せ、自社分だけを持つ。更新は半自動化する |
| Claude Code の仕様変更で動かなくなる | 最低バージョンを定め、更新時にテストを再実行する |
| 外部 API（PyPI・OSV）の障害 | 重大度ごとに障害時の動作を定義する（NFR-02） |

## 17. 用語集

| 用語 | 説明 |
|---|---|
| Claude Code | ターミナルで動く AI コーディングツール |
| Hook | Claude Code が操作をする直前・直後に、必ず実行されるチェック用スクリプト |
| Skill | 必要なときに AI が読み込む、専門知識や手順・振る舞いのまとまり |
| プラグイン | Skill・Hook・コマンドなどを1つにまとめて配布できる、Claude Code の仕組み |
| MCP サーバー | AI に外部のツールやデータを使わせるための接続先 |
| サンドボックス | AI が実行するコマンドの、触れるファイルや通信先を OS レベルで囲い込む仕組み |
| 強制設定ファイル（managed settings） | PC の管理者権限が必要な場所に置く Claude Code の設定ファイル。他の設定より優先され、禁止ルールを上書きできない |
| 許可リスト | 使ってよいものだけを列挙し、それ以外を使えなくする方式 |
| bypass モード | 確認なしで何でも実行する Claude Code の権限モード |
| auto モード | AI の操作を別の判定モデルが審査し、危険なものだけ止める Claude Code の権限モード |
| CLAUDE.md | Claude Code が毎回読み込む、プロジェクトの基本ルールファイル |
| AGENTS.md | AI レビューツール（Codex 等）が読み込む、レビュー基準などを書いたファイル |
| PR（プルリクエスト） | 変更をレビューしてから取り込むための依頼 |
| ブランチ保護 | レビューや検査を通らない変更を取り込めなくする GitHub の設定 |
| Issue | GitHub 上の課題票。不具合の報告や提案を登録する |
| CI / GitHub Actions | コードの変更時に、テストやチェックを自動実行する仕組み |
| Action | GitHub Actions で使う、再利用できる処理の部品 |
| コミット SHA | 変更の1つ1つに付く固有の番号。タグと違って後から書き換えられない |
| コミット前チェック（pre-commit） | コミットの直前に自動で走る検査 |
| Dependabot | 使っている部品の新版が出たときに、更新の PR を自動で作る GitHub の機能 |
| Semgrep | コードの危ない書き方を、ルールに沿って機械的に検出するツール |
| Bandit | Python 専用のセキュリティ検査ツール |
| Ruff | 高速な Python の検査ツール。Bandit と同等のセキュリティルールを持つ |
| gitleaks | API キーなどの秘密情報の混入を検出するツール |
| pip-audit | 使っているライブラリに既知の脆弱性がないか調べるツール |
| osv-scanner | ロックファイルを OSV と照合し、脆弱性や悪性パッケージを調べるツール |
| Trivy | 構成ファイル（Dockerfile、IaC 等）の危ない設定などを検出するツール |
| zizmor | GitHub Actions のワークフローの危ない書き方を検出するツール |
| IaC | クラウドなどのインフラ設定を、コードとして書いて管理する方法 |
| ロックファイル | 使うライブラリのバージョンを、間接的な依存まで含めて固定したファイル |
| 認可 | 「誰に何を許すか」を決める仕組み。漏れがあると、他人のデータが見えるなどの問題が起きる |
| サプライチェーン攻撃 | 使っているライブラリなどに悪意あるコードを仕込む攻撃 |
| スロップスクワッティング | AI がでっち上げたパッケージ名を、攻撃者が先回りして登録しておく攻撃 |
| プロンプトインジェクション | AI が読む文章に指示を紛れ込ませ、AI に意図しない操作をさせる攻撃 |
| cooldown | 公開されて間もない新バージョンを、一定期間入れないようにする設定 |
| OSV | オープンソースの脆弱性・悪性パッケージ情報のデータベース |
| OpenTelemetry | ソフトウェアの動作記録を出力するための共通規格 |
| STRIDE | 脅威を6分類（なりすまし・改ざん・否認・情報漏えい・サービス妨害・権限昇格）で洗い出す手法 |
| 要配慮個人情報 | 病歴・診療情報など、法律上とくに慎重な扱いが求められる個人情報 |
| 3省2ガイドライン | 医療情報を扱う際の安全管理について、厚生労働省と、総務省・経済産業省が定めた2つのガイドラインの総称 |
