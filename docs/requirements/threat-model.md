## 1. この文書について

どんな攻撃や事故がありうるか、このキットでどこまで防げるかを整理する。防げないものも隠さずに書き、何で補うかを示す。

### 判定の意味

| 判定 | 意味 |
|---|---|
| 防げる | 仕組みで機械的に止められる、または見つけられる |
| 多くは防げる | 検査ツールが知っている形のものは見つかる。知らない形のものは残る |
| 一部 | 条件つきで効く、または被害を小さくするだけ |
| 弱い | 助言や AI のレビューに頼っており、見逃しがありうる |
| 対象外 | このキットでは扱わない。別の手段で補う |

## 2. 守るもの

| 守るもの | 漏れたり壊れたりしたときの影響 |
|---|---|
| 秘密情報（API キー、クラウドの鍵、AI ツールの認証情報） | 不正利用、課金、他のシステムへの侵入 |
| ソースコード | 顧客への説明責任、知的財産の流出 |
| 患者データ（歯科案件以降） | 法令上・信頼上の影響が最も大きい |
| CI の権限と秘密情報 | 本番環境やパッケージ公開への侵入 |
| 開発者の PC と GitHub アカウント | 上のすべてへの入口になる |
| キット自体 | 乗っ取られると、全員の PC と全プロジェクトに影響する |

## 3. 想定する原因

| 原因 | 例 |
|---|---|
| 外部の攻撃者 | 悪性パッケージ、正規パッケージや検査ツールの乗っ取り、アカウントの乗っ取り |
| 悪意ある文章 | AI が読むファイルやページに指示を紛れ込ませる（プロンプトインジェクション） |
| AI の誤り | 危ない書き方のコード、でっち上げたパッケージ名、行き過ぎた操作 |
| 人のミス | 秘密情報のコミット、設定の誤り、確認の省略 |

メンバー本人が悪意を持って守りを外すことは想定しない。ルールへの合意を前提に運用する。

## 4. 脅威と対策の一覧

### 4.1 開発中に起きる事故

| ID | 脅威 | 主な対策（要件） | 判定 |
|---|---|---|---|
| T-01 | 秘密情報をコードに書いてしまう | 書く前・コミット前・PR 時の3か所で検査（R-001、FR-10、FR-28、FR-30） | 防げる |
| T-02 | AI が .env や鍵を読んで外へ送る | 読み取り禁止、サンドボックス、通信先の制限（R-002、FR-20、FR-21） | 防げる（Claude 経由の操作に限る） |
| T-03 | AI がでっち上げた名前の悪性パッケージを入れる | 導入前チェック、公開直後の版を入れない設定（R-004、FR-22、FR-23） | 多くは防げる |
| T-04 | 正規のパッケージが乗っ取られる | 公開から7日待つ設定、ロックファイルの検査（FR-23、FR-30） | 一部（7日以内に発覚したものは防げる） |
| T-05 | 悪性の MCP サーバー・Skill・プラグインを入れる | 許可リスト、設定ファイルの検査（R-006、FR-27、FR-26） | 防げる（許可リストに載せる前の審査が前提） |
| T-06 | 開発中の AI が、読んだ文章に操られる | サンドボックス、通信先の制限、読み取り禁止、通知文の安全性（FR-20、FR-21、NFR-13） | 一部（被害を小さくするだけ） |
| T-07 | AI が行き過ぎた操作をする（確認なしの実行、作業フォルダの外への書き込み） | bypass の無効化、サンドボックス（R-003、FR-21、FR-29） | 防げる |
| T-08 | 検査ツールや Action が乗っ取られる | バージョンの固定、最小権限、検査に秘密情報を渡さない（FR-35、FR-51） | 防げる |
| T-09 | メンバーのアカウントが乗っ取られ、悪性のワークフローやスクリプトを入れられる | 全メンバーの2要素認証、CI に長く使える秘密情報を置かない、ワークフロー変更のレビュー必須（FR-75、FR-37、FR-38） | 一部 |
| T-10 | キット自体が乗っ取られる | PR 経由のみの変更、ブランチ保護、バージョンの固定（NFR-08、FR-75） | 一部 |
| T-11 | 人がターミナルで直接入れたパッケージの悪性コードが動く | cooldown、インストール時スクリプトの無効化、PR 時のロックファイル検査（FR-23、FR-30） | 一部 |
| T-12 | マルウェアが利用者の設定を書き換えて居座る | 設定の変化の検知、管理されたフックだけを動かす設定（FR-26、FR-76） | 一部 |
| T-13 | 出所の分からないリポジトリを開き、仕込まれた設定が動く | 最新版の利用、開かないルール（NFR-11、要件定義書12章） | 一部（ルールに依存） |
| T-14 | 入力したコードが AI の学習に使われる | 学習利用の設定オフ、商用契約への移行（要件定義書8章） | 防げる（設定オフが前提） |
| T-15 | 患者データを AI や外部サービスに渡してしまう | 開発機に置かない、読み取り禁止、通信先の制限、データ区分（R-005） | 一部（運用に依存） |

### 4.2 書いたコードの弱点（定番の攻撃）

| ID | 脅威 | 主な対策（要件） | 判定 |
|---|---|---|---|
| T-20 | SQL やコマンドへの命令の注入 | Ruff、Semgrep（FR-10、FR-18、FR-30） | 多くは防げる |
| T-21 | 暗号の誤った使い方、危ない設定 | Ruff、Semgrep、Trivy（FR-10、FR-18、FR-30） | 多くは防げる（ファイルに書かれた設定に限る） |
| T-22 | 既知の弱点があるライブラリを使う | pip-audit、osv-scanner（FR-30） | 防げる（公表済みのものに限る） |
| T-23 | 認可の漏れ（他人のデータが見える） | 認可の確認とテストの促し、別ベンダー AI のレビュー、外部診断（FR-15、FR-31、FR-82、FR-84） | 弱い |
| T-24 | 認証・設計・業務の流れの欠陥 | 別ベンダー AI のレビュー、監査役、外部診断（FR-31、FR-60、FR-84） | 弱い |
| T-25 | ログの不足、例外処理の誤り | Semgrep の一部のルール | 弱い |

### 4.3 このキットの対象外

| ID | 脅威 | 補い方 |
|---|---|---|
| T-30 | 開発者の PC がマルウェアに感染する | OS とソフトの更新、ウイルス対策。Lv2 では端末の管理方法を定める（FR-81） |
| T-31 | フィッシングでパスワードを盗まれる | 2要素認証（FR-75）、社員教育 |
| T-32 | 運用中のシステムへの攻撃（不正ログイン、ランサムウェア等） | 監視、バックアップ、外部の診断 |
| T-33 | 画面から設定したクラウドの設定ミス | 設定をファイルに書いて管理し、検査の対象にする |
| T-34 | メンバー本人が悪意を持って守りを外す | ルールへの合意、PR 時のレビュー |

## 5. 残るリスクと補い方

判定が「一部」「弱い」のもののうち、影響が大きい4点。

| 残るリスク | なぜ防ぎきれないか | 補い方 |
|---|---|---|
| 認可の漏れ（T-23） | 「この人がこのデータを見てよいか」は、コードの書き方からは機械的に判定できない | 他人のデータにアクセスできないことのテストを書く。歯科案件では AI レビューを必須にし、リリース前に外部の脆弱性診断を受ける |
| アカウントの乗っ取り（T-09） | 乗っ取られたアカウントは、正規のメンバーと同じ操作ができる | 2要素認証を全員に必須にする。乗っ取られても盗めるものを減らす（CI に長く使える秘密情報を置かない） |
| 人が直接実行するコマンド（T-11、T-12） | フックとサンドボックスが効くのは Claude 経由の操作だけ | プロジェクトの設定（cooldown、スクリプトの無効化）で守る。PR 時の検査で補う |
| プロンプトインジェクション（T-06、T-13） | 業界全体で、根本的な防ぎ方がまだ無い | 起きても被害が小さくなるよう、読めるもの・送れる先を絞る。出所の分からないものを開かない |

このほかの限界。

- 検査ツールが見つけるのは、知られている形の問題だけである。
- 7日以上気づかれない悪性パッケージは、公開から待つ設定をすり抜ける。
- GitHub の有料プランと学習利用の設定オフが済んでいないと、PR 時のチェックと T-14 の対策は働かない。

## 6. 最近の事例との対応

| 時期 | 何が起きたか | このキットでの結果 |
|---|---|---|
| 2026年2月（報告） | 悪性の Skill が配布サイトで多数見つかった | 許可リストに無いものは入らない（FR-27） |
| 2026年2月（公表） | Claude Code に、リポジトリを開いただけで仕込まれた設定が動く欠陥が見つかった（修正済み） | 最新版の利用（NFR-11）と、出所の分からないリポジトリを開かないルールで備える |
| 2026年3月 | 検査ツール Trivy の公式 Action のタグが書き換えられ、CI の秘密情報が盗まれた | コミット SHA で固定していれば影響を受けない（FR-35） |
| 2026年3月 | 上で盗まれた情報を使い、LiteLLM の悪性版が PyPI に公開された（数時間で隔離） | 公開から7日待つ設定により入らない（FR-23） |
| 2026年春 | npm と PyPI で自己増殖するワームが広がり、AI ツールの設定にフックを仕込んで居座った | 待つ設定で多くは入らない。居座りは検知する（FR-26）。npm は最低限の守りのみ（FR-23） |
| 2026年11月 | 乗っ取られたアカウントから、多数のリポジトリに悪性のワークフローやインストール時スクリプトが入れられた | main はレビュー必須で守る。ブランチ上の悪性ワークフローには、秘密情報を置かないことで備える（FR-37、FR-38、FR-75） |

## 7. 見直し

- 四半期に1回の全体見直し（要件定義書12章）で、この文書も見直す。
- 重大な事件が起きたときは、その事例を6章に当てはめ、穴があれば要件と設計に戻す（FR-55）。
