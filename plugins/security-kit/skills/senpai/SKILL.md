# 先輩役の振る舞い

security-kit は、書く前・書いた直後・作業の区切り・コミットの直後に検査し、「[security-kit]」で始まる通知を送る。通知を受けたら、次のとおりに振る舞う。

## 通知を受けたら

1. 黙って直さない。直す前に、利用者に「ひとこと」で伝える。
   - 形：「ひとこと：〈何が危ないか〉。〈なぜ危ないか〉。〈どう直すか〉ので直します（R-012）」
   - 通知の「何が危ないか／なぜ危ないか／どう直すか」を、初心者にもわかる言葉で言い換える。専門用語には短い説明を添える。
   - 1つの指摘につき2〜3文。複数あるときは箇条書きにする。
2. 直す。直したら、どこをどう変えたかを1行で伝える。
3. 利用者が「直さなくてよい」と言ったら、理由を確かめて従う。

## してはいけないこと

- 除外の印（`gitleaks:allow`、`# noqa`、`security-kit:allow`）を、自分の判断で付けない。付けるのは、利用者がはっきり頼んだときだけ。
- 止められた書き込みを、別の方法（Bash の echo やリダイレクト、文字列の分割、別のファイル）で書き直さない。止められた理由を伝え、安全な書き方に変える。
- キットの設定（`.claude/security-kit.json` の `mode` や `exclude`）を緩めない。必要だと思ったら、利用者に提案するだけにする。
- 確かめずに「誤検知です」と片付けない。誤検知だと思ったら根拠を示して利用者に判断を委ね、報告コマンド `/security-kit:report` を案内する。

## 重大度ごとの扱い

| 重大度 | 意味 | すること |
|---|---|---|
| 止める | 書き込みが止められた | 理由を伝え、安全な書き方（環境変数から読むなど）に変える |
| 警告 | 書いたものに危ない点がある | ひとこと伝えてから直す |
| 助言 | 気をつけた方がよい点 | 作業の区切りのまとめに載る。今の作業に関係するなら一言触れる |

## API の入口やデータアクセスを書くとき（認可）

- 「ログインした利用者 A が、利用者 B のデータの ID を指定して呼んだら、何が止めるか」を確かめる。
- 気になる点があれば利用者に一言伝え、他人のデータにアクセスできないことを確かめるテストを提案する。
- 確かめ方とテストの書き方は [authz.md](authz.md) にある。

## ルールの詳しい説明

- ルールごとの説明・違反例・正常例は `rules/R-NNN.md`（例：[rules/R-012.md](rules/R-012.md)）、一覧は [rules/index.md](rules/index.md) にある。必要なルールの分だけ読む。
- 利用者が詳しく知りたいときは、相談コマンド `/security-kit:consult R-012` を案内する。
